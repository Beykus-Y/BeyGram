# Яндекс Музыка как второй источник музыки (ADR)

Статус: предложение, код не написан. Дата исследования: 11 ноября 2026 г. Область: только DEV-сборка, опциональная экспериментальная настройка «Вход в Yandex ID».

Документ отвечает на три вопроса: можно ли брать музыку, тексты и плейлисты из Яндекс Музыки; каким способом это делать; как встроить это в плеер BeyGram, не ломая то, что уже есть.

## Короткий вывод

1. Технически это выполнимо. Протокол Яндекс Музыки хорошо описан сообществом, вход работает без ввода пароля в BeyGram, есть прямые ссылки на аудио, синхронные тексты, плейлисты, «Моя волна» и лайки.
2. Рекомендация: **свой небольшой клиент на Kotlin внутри BeyGram**, написанный по открытому описанию протокола MarshalX (OpenAPI), без новых зависимостей. YaMusicSDK использовать как образец, а не как зависимость. Внешний прокси-сервер не делать.
3. Главный риск не технический. API неофициальный, клиент выдаёт себя за официальное приложение Яндекса, и есть задокументированный случай блокировки аккаунта целиком. Поэтому функция должна жить только в DEV-варианте, за явным предупреждением, и первые проверки надо делать на отдельном аккаунте Яндекса, а не на основном.
4. В плеер источник встраивается по уже существующему образцу музыкальных ботов (`BotTrackResolver`): строка очереди без файла, файл появляется лениво в приватном кэше. Так BG Mix, анализ тишины, кроссфейд и мини-плеер работают без переписывания.

## Как устроен протокол

### Вход

- **OAuth Device Flow** на `oauth.yandex.ru`: приложение запрашивает код устройства, показывает пользователю короткий код и адрес страницы Яндекса, затем опрашивает сервер, пока пользователь не подтвердит вход. Ответ содержит `access_token`, `refresh_token` и `expires_in`.
- Пароль в BeyGram не вводится и через BeyGram не проходит. Пользователь подтверждает вход в своём браузере или в приложении Яндекса.
- Срок жизни токена около года (в документации MarshalX пример `expires_in=31535645`). Есть `refresh_token`. Библиотеки сами токен не обновляют и не хранят.
- Важная оговорка: собственного зарегистрированного OAuth-приложения с доступом к Музыке получить нельзя, таких прав Яндекс сторонним разработчикам не выдаёт. Обе библиотеки используют идентификатор и секрет официального Android-приложения Яндекс Музыки. YaMusicSDK принимает их параметром, MarshalX хранит значением по умолчанию.
- Запасной способ (страница входа Яндекса во встроенном WebView с перехватом токена из адреса) хуже: пароль вводится внутри BeyGram. Не рекомендуется.

### Подписка

`GET /account/status` возвращает данные аккаунта и признак `plus.has_plus`. Без подписки сервер отдаёт только 30-секундные фрагменты. BeyGram должен проверять признак сразу после входа и не играть фрагменты под видом треков.

### Ссылки на аудио

Есть два способа, оба требуют токен.

| | Старый: `/tracks/{id}/download-info` | Новый: `/get-file-info` |
| --- | --- | --- |
| Качество | MP3 до 320 кбит/с | `nq`, `hq`, `lossless`; кодеки FLAC, AAC, HE-AAC, MP3 |
| Как получить ссылку | Ответ ведёт на XML, из его полей и постоянной «соли» считается MD5, получается адрес `…/get-mp3/…` | Запрос подписывается HMAC-SHA256 ключом настольного клиента, ключ привязан к заголовку `X-Yandex-Music-Client` |
| Срок жизни | Прямую ссылку надо запросить в течение одной минуты после `download-info`, иначе ответ 410 | Точный срок не описан; ссылку надо считать одноразовой и короткоживущей |
| Шифрование | Нет | Доставка `raw` (обычный файл) или `encraw` (AES-128-CTR с нулевым счётчиком, ключ приходит в том же ответе) |

Выводы для BeyGram:

- Ссылки нельзя сохранять в очереди, в сохранённой сессии плеера и в библиотеке. Хранится только идентификатор трека, ссылка запрашивается в момент скачивания. На ответы 403 и 410 клиент запрашивает новую ссылку один раз.
- Начинать с `/get-file-info`, качество `hq`, доставка `raw`, с откатом на `download-info`. Lossless оставить на потом.
- Доставку `encraw` не использовать. Расшифровка технически простая, но это обход технического средства защиты, то есть отдельный юридический риск (ст. 1299 ГК РФ). Обычный `raw` даёт то же аудио.

### Тексты

- У трека есть `lyricsInfo` с признаками `hasAvailableSyncLyrics` и `hasAvailableTextLyrics`.
- `GET /tracks/{id}/lyrics?format=LRC|TEXT` с подписью HMAC (ключ Android-клиента) возвращает адрес файла текста, авторов и правообладателя текста. `LRC` содержит метки времени по строкам, этого достаточно для подсветки текущей строки и перехода по нажатию на строку.
- В YaMusicSDK текстов нет вообще (поля закомментированы). Это одна из причин не брать его зависимостью.
- Правообладателя текста (обычно сторонний поставщик) надо показывать под текстом, как это делает официальный клиент.

### Плейлисты, лайки, рекомендации

- Плейлисты пользователя, плейлист по `uid` и `kind`, создание, удаление, добавление и удаление треков (через разностные операции с номером ревизии).
- «Мне нравится»: список с ревизией, лайк и дизлайк.
- Главная страница: персональные плейлисты, «Плейлист дня», чарт, новинки.
- «Моя волна» и станции (rotor): старт сессии, следующая пачка треков, обратная связь (начало, конец, пропуск). Без обратной связи волна не подстраивается.
- Поиск с типами и подсказками.
- `/play-audio`: отчёт о прослушивании. Официальные клиенты шлют его всегда; от него зависят история, рекомендации и, по всей видимости, учёт прослушиваний для правообладателей. BeyGram должен слать честные отчёты.
- Ynison (синхронизация плеера между устройствами по WebSocket) есть у MarshalX. Для BeyGram не нужен.

### Лимиты и блокировки

- Лимиты не документированы. Сервер отвечает 429 с заголовком `Retry-After`. В YaMusicSDK есть продуманный ограничитель: общая пауза на аккаунт после 429, один пробный запрос, затем пять запросов с шагом 250 мс; события прослушивания не повторяются. Эту схему стоит перенять.
- Задокументированный случай блокировки: пост на Хабре от 06.02.2026 ([ссылка](https://habr.com/ru/posts/993408/)). Автор через неофициальный API переносил плейлисты из Spotify, после чего с ноября 2025 г. аккаунт получает `403 API access restricted` во всех клиентах, включая официальные приложения и колонки. Поддержка не решила вопрос за три с лишним месяца, подписка при этом оплачивалась.
- API меняется без предупреждений. У MarshalX за октябрь 2026 г. три выпуска, два из них только из-за расхождения моделей с сервером. Ключи подписи привязаны к версии официального клиента и могут быть заменены.

### Сеть

Яндекс Музыка работает только из своих регионов. BeyGram-запросы по умолчанию идут через локальный прокси, когда он запущен (`MihomoProxyClient.openConnection`), а его выход обычно за границей. Запросы к Яндексу должны идти **напрямую, в обход локального прокси** (`openConnection(url, proxy = null)`), иначе сервис ответит, что недоступен в регионе. Это надо проверить на устройстве на этапе 0.

| Зрелость | 19 коммитов, один автор, одна звезда | Наша ответственность, но код маленький и покрыт JVM-тестами | Зрелая библиотека |
| Токен | На устройстве | На устройстве | На сервере или проходит через него |

| Юридически | LGPL-3.0 совместима с GPL-3.0 BeyGram | Чисто: свой код по описанию протокола | Худший вариант: мы становимся посредником, который раздаёт чужой контент |
| Обновления протокола | Ждём автора или правим форк | Сверяемся с `openapi.json` и выпусками MarshalX | Обновляем сервер без выпуска приложения |

**Рекомендация: вариант B.** Вариант A даёт мало готового: недостающие части (тексты, новый способ получения файла) всё равно писать самим, а взамен приходят две новые зависимости и чужой молодой код. Из YaMusicSDK стоит взять идеи: ограничитель запросов, запрет `DOCTYPE` и `ENTITY` при разборе XML, типизированный результат вместо исключений. Вариант C отвергнут: единственный его плюс (обновление без выпуска) не окупает сервер, хранение чужих токенов и юридическую роль посредника.

## Как это ложится на BeyGram

### Что уже есть и переиспользуется

- `PlaybackItem` может быть без пути к файлу: `PlaybackSourceHandle` разрешает его лениво.
- `BotTrackResolver` и `MusicBotCache` уже решают ту же задачу для музыкальных ботов: ключ с префиксом `bot:`, файл скачивается, когда строка становится текущей или следующей, копия живёт в приватном кэше и удаляется, когда её больше нечему играть. Неудачная строка пропускается политикой ошибок.
- `GrowingPlaybackSource` позволяет играть файл, который ещё дописывается.
- После PR #740 очередь всегда стартует на обычном плеере, а BG Mix подхватывает трек, когда файл скачан целиком. Для Яндекса это поведение подходит без изменений.
- `PlaybackSourceLabel` показывает в плеере, откуда трек.
- `DiagnosticsRedactor` вычищает токены и секреты из отчётов.

### Что добавить

```
domain/music/MusicProvider.kt        интерфейс источника: поиск, библиотека, плейлист, текст, волна
data/yandex/ (в app/src/dev)         клиент API, вход, модели, ограничитель, хранилище токена
playback/LazyTrackResolver.kt        общий реестр ленивых источников по префиксу ключа
playback/YandexTrackResolver.kt      ключ ym:<trackId>, скачивание в кэш, отчёты play-audio
ui/screens/yandex/                   вход, карточка аккаунта, разделы музыки, текст песни
res/values*/strings_yandex_music.xml строки на всех языках интерфейса
```

1. **Интерфейс источника.** `MusicProvider` с возможностями (`search`, `likedTracks`, `playlists`, `playlistTracks`, `lyrics`, `stations`). Telegram получает тонкую обёртку над существующим кодом, чтобы экраны музыки работали с обоими источниками одинаково. В `main` лежит только интерфейс и заглушка «источник недоступен»; реализация Яндекса лежит в `app/src/dev/`, в Stable её нет физически.
2. **Ленивые источники.** Сейчас в `PlaybackSourceHandle` зашито `BotTrackResolver.isBotKey(...)`. Заменить на реестр по префиксу ключа (`bot:`, `ym:`), чтобы третий источник не добавлял условий в плеер.
3. **Идентичность трека.** `PlaybackItem.fileId` и `origin` остаются пустыми, ключ `ym:<trackId>:<albumId>`, отдельный `accountId` вида `yandex:<uid>`, чтобы очередь не смешивалась с аккаунтами Telegram по правилам `PlaybackQueueSource`.
4. **Скачивание.** Первая версия: трек скачивается целиком в `cacheDir/music-yandex/`, затем играет с диска. Текущий трек и один следующий, не больше. Вторая версия: файл дописывается, плеер читает его через `GrowingPlaybackSource` и стартует сразу.
5. **Анализ тишины, кроссфейд, BG Mix.** `SilenceAnalyzer.isMeasurable` требует `fileId`, а ключ кэша собран как `accountId:fileId`. Нужна небольшая правка: мерить любой завершённый файл со стабильным ключом (`item.key`). Кроссфейд и BG Mix работают с готовыми файлами и изменений не требуют. Надо проверить, что нативный декодер BG Mix читает выбранный кодек (MP3, AAC и FLAC проверить в BG-Media), и выбирать кодек с учётом этого.
6. **Кэш.** Приватный каталог, вне резервных копий, с лимитом (по умолчанию 1 ГБ, вытеснение давно не игравших), очищается при выходе из Яндекса и кнопкой в настройках. Загрузка плейлиста целиком «впрок» в первой версии не делается: это и есть поведение, за которое блокируют.
7. **Запреты для треков Яндекса.** Скрыть «Поделиться файлом», «Переслать», «В профиль», экспорт в `.bgmusic`, сохранение в файлы. В локальные плейлисты BeyGram трек попадает ссылкой на идентификатор, а не файлом. Поделиться можно только ссылкой на трек в Яндекс Музыке.
8. **Отчёты о прослушивании.** `/play-audio` на старте и в конце трека, обратная связь волны при пропуске. Отправка не повторяется и не блокирует воспроизведение.

### Токен

- Хранить в приватном файле настроек, зашифрованным ключом из Android Keystore (AES-GCM). В проекте Keystore пока не используется, это новый маленький класс `SecretStore`. Библиотеку `security-crypto` не подключать: она объявлена устаревшей.
- Исключить файл из резервных копий: в манифесте включён `allowBackup`, значит файл надо добавить в `data_extraction_rules.xml` и `backup_rules.xml`.
- Токен не попадает в логи, в сохранённую сессию плеера, в отчёты диагностики и в аналитику. Адреса с подписями (`get-mp3`, файл текста) тоже не логируются: в лог идёт только путь метода и код ответа.
- `DiagnosticsRedactor` дополнить правилом для заголовка `Authorization: OAuth …` и для токенов Яндекса по их виду. В отчёт диагностики идёт только: источник подключён или нет, есть ли подписка, код последней ошибки.
- Ответ 401 переводит источник в состояние «нужно войти заново», токен стирается. Выход из Яндекса стирает токен, кэш аудио и кэш метаданных.
- Мультиаккаунт Telegram: вход в Яндекс один на приложение, а не на аккаунт Telegram.

### Сеть и нагрузка

- Все запросы к Яндексу идут напрямую, одной очередью, не чаще примерно четырёх в секунду, с паузой по `Retry-After`.
- Метаданные кэшируются: список лайков по номеру ревизии, плейлисты на время сессии, тексты на диск рядом с треком.
- Заголовки клиента и ключи подписи собраны в одном файле `YandexClientIdentity.kt`, чтобы их замена была правкой одного места.

## Интерфейс

- **Вход.** Настройки, раздел «Экспериментальное», пункт «Вход в Yandex ID». Экран входа: предупреждение о неофициальном доступе и риске для аккаунта с явным согласием, затем код, кнопка «Открыть Яндекс» и QR-код для подтверждения с другого устройства, обратный отсчёт срока кода.
- **Карточка аккаунта.** Имя, состояние подписки, качество звука, размер кэша и очистка, выход. Без подписки вместо музыки показывается понятное объяснение.
- **Музыка.** На экране «Моя музыка» появляется блок «Яндекс Музыка»: «Моя волна», «Мне нравится», плейлисты, «Плейлист дня». В поиске музыки переключатель источника. Пока входа нет, блока нет вовсе.
- **Плеер.** Подпись источника, кнопка лайка, кнопка текста. Экран текста: подсветка текущей строки, плавная прокрутка, переход по нажатию на строку, подпись правообладателя текста. Мини-плеер без изменений.
- **Общие правила.** Только компоненты дизайн-системы, чтобы экраны сами получили все стили и темы (Material 3, Liquid Glass и остальные) и попали в матрицу `docs/style-coverage-632.md`. Движение через Motion Engine. Все строки в ресурсах на всех языках интерфейса, тесты покрытия строк должны проходить. Снимки экранов добавить в Roborazzi. В интерфейсе нет слов про внутренние библиотеки и про «API»; сервис называется «Яндекс Музыка», вход называется «Yandex ID».

## Этапы

| Этап | Содержание | Результат |
| --- | --- | --- |
| 0. Проверка на живом аккаунте | Клиент на JVM с тестами: вход по коду, статус подписки, `/get-file-info` и `download-info`, срок жизни ссылки, прямой маршрут мимо прокси, какие кодеки читает BG Mix | Решение «идём дальше» с цифрами вместо предположений |

| 2. Воспроизведение | Реестр ленивых источников, `YandexTrackResolver`, кэш, подпись источника, «Мне нравится» и плейлисты на чтение, отчёты о прослушивании, запреты на пересылку | Плейлист Яндекса играет в общем плеере и мини-плеере |
| 3. Поиск и тексты | Переключатель источника в поиске, экран текста с синхронной подсветкой | Основная польза для слушателя |
