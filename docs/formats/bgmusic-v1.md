# Формат `.bgmusic`, версия 1

Часть задачи #639 «BeyGram Music Collections», слайс B (Format). Реализация: пакет
`com.beykus.beygram.data.music.bgmusic`. Все числа ниже взяты из констант в
`BgMusicFormat.kt`, поэтому документ и код не должны расходиться.

## 1. Что это и чего это не делает

`.bgmusic` — **снимок** плейлиста в переносимом виде.

- **Это не синхронизация.** Изменения исходного плейлиста или другого устройства в файл не попадают.
  Файл импортируется заново, как новый снимок.
- **Это не доступ к аудио.** Аудиофайлы в архив не входят, и получатель не получает права их слушать.
  Подсказки `sources` (раздел 5) показывают, где трек можно найти, но ничего не гарантируют.
- В файл попадает только то, что перечислено в разделах 3 и 4. Остальное не пишется (раздел 9).

## 2. Контейнер

- ZIP. Записи могут быть `stored` или `deflated`; читатель принимает оба метода.
- MIME-тип: `application/vnd.beygram.music+zip`. Расширение: `.bgmusic`.
- Обязательная запись: `manifest.json`. Рекомендуется первой, но читатель порядок не проверяет.
- Необязательная запись: одна обложка, `cover.webp`, `cover.jpg` или `cover.png` (раздел 4).
- Поле `format` в манифесте (`"beygram.music"`) идентифицирует формат. Это **не** криптографическая
  подпись: подделать файл она не мешает.
- Имя файла на импорт не влияет. Решение принимается по содержимому. Подсказка `looksLikeCandidate`
  по имени и MIME-типу нужна только для фильтра в диалоге выбора файла.

### 2.1. Имена записей

- Только ASCII: `A–Z`, `a–z`, `0–9`, `.`, `_`, `-`. Первый символ — буква или цифра. Длина не больше 100.
- Запрещены: `/`, `\`, `..`, `:`, пустое имя, имена каталогов (заканчиваются на `/`), абсолютные пути.
- Повтор имени запрещён, в том числе без учёта регистра: `Manifest.json` и `manifest.json` — повтор.
- Вложенные архивы запрещены. Проверка двойная: по расширению (`.zip`, `.bgmusic`, `.jar`, `.apk`, `.7z`,
  `.rar`, `.tar`, `.gz`, `.tgz`, `.bz2`, `.xz`) и по сигнатуре содержимого (ZIP, gzip, 7z, RAR, bzip2, xz).
  Сигнатура проверяется у любой записи, в том числе неизвестной.
- Неизвестные безопасные записи пропускаются, чтобы будущие версии оставались читаемыми. Они учитываются
  в лимитах (раздел 6).

## 3. `manifest.json`

Кодировка UTF-8. BOM допускается и отбрасывается. Писатель создаёт строгий JSON (RFC 8259) с фиксированным
порядком ключей. `null` никогда не записывается текстом `"null"`.

Читатель принимает только строгий JSON по RFC 8259. Одинарные кавычки, комментарии, `;`, `=`, слова без кавычек,
запятые перед закрывающей скобкой, данные после значения и управляющие символы внутри строк отвергаются
(`BadJson`). Повторяющийся ключ в одном объекте тоже отвергается (`BadJson`). Вложенность не больше 16 уровней
(раздел 11, пункт 5).

### 3.1. Поля верхнего уровня

| Поле | Тип | Обязательно | Правила |
|---|---|---|---|
| `format` | строка | да | ровно `"beygram.music"`. Иначе ошибка `BadSignature` |
| `format_version` | целое | да | не меньше 1. Версия, в которой записан файл. v1 пишет `1` |
| `min_reader_version` | целое | да | от 1 до `format_version` включительно. Минимальная версия читателя для корректного чтения |
| `playlist_id` | строка | да | UUID в виде `8-4-4-4-12` hex. Читатель принимает любой регистр и приводит к нижнему |
| `revision` | целое | да | от 0 до 2^63−1. Счётчик, который владелец увеличивает при каждом изменении |
| `title` | строка | да | после очистки от 1 до 128 символов |
| `description` | строка | нет | до 1000 символов. Переводы строк сохраняются (раздел 7). Отсутствие и `null` читаются как пустая строка |
| `updated_at` | целое | да | миллисекунды Unix-времени, UTC. От 0 до 253402300799999 |
| `author` | объект | нет | `{"name": "…"}`, имя от 1 до 128 символов. Пишется **только с явного согласия** (раздел 9) |
| `tracks` | массив | да | от 0 до 5000 элементов. Порядок значим и сохраняется |

### 3.2. Элемент `tracks`

| Поле | Тип | Обязательно | Правила |
|---|---|---|---|
| `id` | строка | да | UUID: стабильный идентификатор элемента. Уникален внутри файла |
| `title` | строка | да | после очистки от 1 до 256 символов |
| `artist` | строка | да | до 256 символов. Может быть пустой |
| `album` | строка | да | до 256 символов. Может быть пустой |
| `duration_sec` | целое | да | от 0 до 604800 (7 суток). `0` означает «неизвестно» |
| `audio_hash` | строка | нет | `sha256:` и 64 строчных hex-символа. Пишется только если хеш реально вычислен |
| `sources` | массив | нет | подсказки о месте трека (раздел 5). Не больше 8 подсказок |

### 3.3. Пример

```json
{
  "format": "beygram.music",
  "format_version": 1,
  "min_reader_version": 1,
  "playlist_id": "6f1d2c3a-4b5e-4f60-8a7b-9c0d1e2f3a4b",
  "revision": 3,
  "title": "Утро",
  "description": "",
  "updated_at": 1700000000000,
  "tracks": [
    {
      "id": "0d6f3c1e-7a2b-4c5d-9e8f-1a2b3c4d5e6f",
      "title": "Song",
      "artist": "Artist",
      "album": "",
      "duration_sec": 215,
      "sources": [{"type": "telegram_public", "username": "some_channel", "message_id": 42}]
    }
  ]
}
```

## 4. Обложка

- Одна запись `cover.webp`, `cover.jpg` или `cover.png`, не больше 1 MiB (несжатый размер).
- Тип определяется по содержимому, а не по расширению:
  WebP — байты 0–3 `RIFF` и байты 8–11 `WEBP`; JPEG — `FF D8 FF`; PNG — `89 50 4E 47 0D 0A 1A 0A`.
- Имя записи должно соответствовать содержимому. Иначе ошибка `BadCover`, в том числе для пустой записи.
- Писатель выбирает имя по magic bytes сам. Другие форматы (GIF и прочие) он отвергает.
- Обложка необязательна. Если её нет, поле `cover` в результате чтения равно `null`.

## 5. Подсказки источников (`sources`)

v1 определяет один тип:

```json
{"type": "telegram_public", "username": "channel_name", "message_id": 42}
```

- `username` — публичный username канала или группы **без** `@`. Длина от 5 до 32 символов: латиница,
  цифры и `_`, первый символ — буква.
- `message_id` — целое от 1 до 2147483647.
- Пишутся **только публичные** посты. Приватные чаты, числовые id чатов, `file_id`, пути к файлам и номера
  телефонов в файл не попадают никогда.
- Читатель отбрасывает подсказки неизвестного типа, битые и не относящиеся к v1, не затрагивая остальной
  файл. Поле `sources` при этом должно быть массивом, иначе `BadField`.

Подсказка не даёт доступа к аудио: пост могут удалить, канал закрыть или переименовать.

## 6. Лимиты и причины отказа

| Что ограничено | Лимит | Причина отказа |
|---|---|---|
| Файл целиком, сжатый | 4 MiB | `TooLarge` |
| Суммарный распакованный объём всех записей | 4 MiB | `TooLarge` |
| `manifest.json`, распакованный | 2 MiB | `ManifestTooLarge` |
| Обложка, распакованная | 1 MiB | `CoverTooLarge` |
| Количество записей | 8 | `TooManyEntries` |
| Количество треков | 5000 | `TooManyTracks` |
| Подсказок на один трек | 8 | лишние отбрасываются при чтении; писатель отказывается |
| Вложенность JSON | 16 уровней | `BadJson` |
| Название плейлиста | 128 символов | обрезается |
| Описание | 1000 символов | обрезается |
| Название трека | 256 символов | обрезается |
| Исполнитель, альбом | 256 символов | обрезаются |
| Имя автора | 128 символов | обрезается |
| Имя записи ZIP | 100 символов ASCII | `BadEntryName` |

Правила:

- Читатель **не доверяет** размерам, заявленным в архиве. Байты считаются при чтении, и чтение прерывается
  при превышении лимита, даже если заголовок записи говорит иначе. Так работает защита от zip-бомб: 50 MB
  нулей сжимаются примерно до 50 KB, но читатель отвергает их как `ManifestTooLarge`, как только распакованный
  манифест превышает 2 MiB.
- Суммарный лимит распакованного объёма ограничивает и коэффициент сжатия: файл не может развернуться
  больше разрешённого, сколько бы ни было записей.
- Строки, длиннее лимита, **обрезаются** (по символам, не по байтам UTF-16), а не отвергаются.
  Обрезание не разрывает суррогатные пары.
- Писатель отказывается от записи, если манифест больше 2 MiB, и ничего не пишет.

### 6.1. Все причины отказа (`BgMusicInvalidReason`)

| Причина | Значение |
|---|---|
| `TooLarge` | файл или распакованный объём больше лимита; также нехватка памяти при разборе (`OutOfMemoryError`) |
| `NotZip` | вход короче 4 байт или не начинается с сигнатуры локальной записи ZIP `50 4B 03 04`. Пустой ZIP без записей начинается с другой сигнатуры и получает эту причину |
| `CorruptArchive` | ZIP повреждён или обрезан, в том числе обрыв сразу после сигнатуры первой записи; запись зашифрована или сжата методом, кроме `stored` и `deflated` |
| `IoError` | ошибка источника данных при чтении или прерывание потока (поток остаётся помеченным как прерванный). Сам файл может быть корректным; нужен повтор, а не сообщение «файл повреждён» |
| `MissingManifest` | нет `manifest.json` |
| `BadEntryName` | небезопасное имя, каталог или вложенный архив |
| `DuplicateEntry` | повтор имени (без учёта регистра) или вторая обложка |
| `TooManyEntries` | больше 8 записей |
| `ManifestTooLarge` | манифест больше 2 MiB |
| `CoverTooLarge` | обложка больше 1 MiB |
| `BadJson` | манифест не UTF-8, не строгий JSON (раздел 3), не объект, повторяет ключ в одном объекте или вложен глубже 16 уровней |
| `BadSignature` | нет поля `format` или значение другое |
| `BadField` | нет обязательного поля, неверный тип или диапазон, повтор `id` трека, `sources` не массив |
| `TooManyTracks` | больше 5000 треков |
| `BadCover` | содержимое обложки не соответствует имени записи |

Результат `Unsupported` не относится к ошибкам: это файл, который требует более новой версии читателя.

Отмена корутины (`CancellationException`) не становится причиной отказа: она пробрасывается вызывающему коду.

## 7. Очистка текста

Одинаково при записи и при чтении, поэтому записанный файл читается без изменений. Очистка идемпотентна:
повторная очистка уже очищенного текста ничего не меняет.

Переводами строк считаются CR, LF, VT (U+000B), FF (U+000C), NEL (U+0085), LINE SEPARATOR (U+2028) и
PARAGRAPH SEPARATOR (U+2029). Пара CRLF считается одним переводом.

1. В однострочных полях (название плейлиста и трека, исполнитель, альбом, имя автора) каждый перевод строки
   становится одним пробелом, чтобы слова не склеивались. В описании каждый перевод становится LF, а больше
   двух LF подряд сокращаются до двух.
2. Табуляция (U+0009) становится одним пробелом во всех полях.
3. Удаляются прочие управляющие символы U+0000–U+0008, U+000E–U+001F и U+007F–U+009F, кроме U+0085 из пункта 1.
   Удалённый символ невидим, поэтому он не разрывает серию переводов строк: `a`, LF, U+0007, LF, LF, `b` даёт `a`, LF, LF, `b`.
4. Удаляются символы двунаправленного форматирования U+202A–U+202E и U+2066–U+2069, а также невидимые метки
   U+061C (ALM), U+200B (ZWSP), U+200E и U+200F (LRM, RLM) и U+FEFF (BOM). Это защита от подмены текста:
   невидимыми символами можно скрыть или переставить слова. ZWJ (U+200D) сохраняется: без него не склеиваются
   составные эмодзи.
5. Удаляются непарные суррогаты.
6. Пробелы и переводы строк по краям обрезаются.
7. Строка обрезается по лимиту, в символах (code points). После обрезки пробелы и переводы строк у конца
   снова обрезаются.

## 8. Совместимость версий

- Читатель v1 понимает `min_reader_version` равный 1.
- `min_reader_version` больше 1 даёт `Unsupported(format_version, min_reader_version)`. Такой файл не
  импортируется. Локальные данные не меняются, сам файл не изменяется и не удаляется. Пользователю
  сообщают, что нужна новая версия BeyGram.
- Файл с `format_version` больше 1, но `min_reader_version` равным 1, читается. Неизвестные поля игнорируются.
- Неизвестные поля на любом уровне (верхний уровень, трек, подсказка, автор) игнорируются.
- Версия проверяется до остальных полей. Поэтому новый файл с другой структурой даёт `Unsupported`, а не
  ложную ошибку `BadField`.
- Правило для будущих изменений: всё, что старый читатель не может проигнорировать, повышает
  `min_reader_version`.

## 9. Приватность: что по умолчанию не пишется

В файл по умолчанию не попадает:

- числовые id чатов и каналов, в том числе приватных; ссылки-приглашения; `file_id` и другие внутренние
  идентификаторы TDLib;
- пути на устройстве и имена локальных файлов;
- номер телефона, id и username владельца аккаунта, данные других пользователей;
- приватные источники (разрешены только публичные username, раздел 5);
- история прослушивания, статистика, даты добавления треков;
- `audio_hash`, пока хеш явно не вычислен. Хеш не называет трек, но позволяет сравнивать файлы;
- `author`. Имя автора пишется только с явного согласия пользователя в момент экспорта;
- токены, ключи и данные сессии.

`playlist_id` и `id` треков должны быть случайными UUID версии 4, которые генерирует приложение. Их нельзя
выводить из Telegram-данных, аккаунта или путей, иначе по ним можно связать файл с аккаунтом.

Экспорт, в котором есть автор или подсказки на публичные посты, показывает пользователю, что именно
попадёт в файл.

## 10. Импорт и дубликаты

Решение принимается по паре `(playlist_id, revision)` относительно локальных плейлистов. Функция:
`BgMusicImportDecision.decide(playlistId, revision, existing)`.

| Ситуация | Результат | Что предложить |
|---|---|---|
| Локального плейлиста с таким `playlist_id` нет | `NewPlaylist` | импортировать как новый |
| Есть, `revision` совпадает | `SameRevision` | «уже импортирован»; ничего не менять |
| Есть, `revision` в файле больше | `NewerRevision` | обновить: объединить, заменить или импортировать копией |
| Есть, `revision` в файле меньше | `OlderRevision` | предупредить; импортировать копией или отменить |

Правила:

- Ничего не заменяется, не объединяется и не копируется **молча**. Выбор всегда делает пользователь.
- `merge` сопоставляет треки по `id`. Новые добавляются, изменённые метаданные обновляются. Удаления
  применяются только после отдельного подтверждения.
- `replace` заменяет локальный плейлист целиком, после подтверждения.
- `copy` создаёт новый плейлист с новым `playlist_id`, чтобы история ревизий исходного не смешивалась.
- Сравнение `playlist_id` не зависит от регистра. Если в локальной базе один id встречается несколько раз,
  берётся наибольшая ревизия.

## 11. Принятые решения

Вопросы, открытые при первой версии, решены. Ниже решение и причина.

1. **Лимит манифеста 2 MiB** (`MAX_MANIFEST_BYTES`, раньше 1 MiB). При лимите 1 MiB 5000 треков с типичной
   кириллицей не записывались. Замер писателя, JSON манифеста в байтах; служебная часть пустого манифеста
   212 байт; кириллица занимает 2 байта на символ:
   - короткие ASCII-названия (15/10/10 символов): 134 байта на трек, 5000 треков занимают 670 211 байт;
   - кириллица (40/25/25 символов): 279 байт на трек, 5000 треков занимают 1 395 211 байт;
   - кириллица (80/60/60 символов): 499 байт на трек, в 2 MiB входит около 4200 треков;
   - кириллица (256/256/256 символов): 1635 байт на трек, в 2 MiB входит около 1280 треков;
   - кириллица (40/25/25) и 8 подсказок источников с 32-символьными username: 1067 байт на трек, в 2 MiB
     входит около 1965 треков.

   5000 треков укладываются, если на трек в среднем приходится не больше 419 байт JSON. Манифест больше
   2 MiB отвергается целиком, и писатель ничего не записывает. Лимит файла 4 MiB и суммарный лимит
   распакованных данных 4 MiB не меняются: манифест 2 MiB и обложка 1 MiB дают 3 MiB.
2. **Переводы строк в описании сохраняются.** CRLF и CR становятся LF, LF остаётся, больше двух переводов подряд
   сокращаются до двух (раздел 7). В однострочных полях перевод строки становится пробелом, поэтому слова не
   склеиваются. Табуляция везде становится пробелом.
3. **Повторяющийся ключ в одном объекте отвергается** (`BadJson`) на обеих платформах. Писатель ключи не повторяет.
   Прежнее решение «оставить как есть» пересмотрено: JVM отвергал такой файл, а Android брал последнее значение,
   и результат зависел от платформы. Ключи сравниваются после распаковки escape-последовательностей: `"a"`
   и `"a"` — один и тот же ключ.
4. **Отклонения от исходного брифа приняты:**
   - причины `CorruptArchive` (повреждённый или обрезанный ZIP, шифрование) и `IoError` (ошибка источника)
     добавлены к списку; у `Invalid` есть поле `detail` со служебной строкой без пользовательского текста
     (раздел 6.1);
   - `BgMusicSourceHint` — sealed-класс, его единственный вариант в v1 — `TelegramPublic`;
   - безопасные неизвестные записи пропускаются, но учитываются в лимитах записей и распакованного объёма;
     вложенные архивы отвергаются (раздел 2.1);
   - чтение мягкое для текстов и подсказок: длинные строки обрезаются, битый `audio_hash` и некорректные
     `sources` отбрасываются; структура, обязательные поля и числа проверяются строго (разделы 3 и 5);
   - `Unsupported` возвращается только при `min_reader_version` больше 1 (раздел 8).
5. **Строгий JSON до разбора.** org.json принимает лишнее: одинарные кавычки, комментарии (`#`, `//`, блочные),
   слова без кавычек, разделители `;` и `=`, а Android-версия читает и данные после значения. Подсчёт вложенности
   по тексту на таком вводе можно обмануть, например одинарной кавычкой с `"` внутри. Поэтому перед разбором текст
   проверяется итеративно по грамматике RFC 8259, с лимитом вложенности 16 уровней и проверкой повторных ключей
   (`BgMusicStrictJson`). Парсер видит только строгий JSON, и обе платформы читают один и тот же файл одинаково.

## 12. Реализация

Пакет `com.beykus.beygram.data.music.bgmusic`:

- `BgMusicModels.kt` — DTO: `BgMusicManifest`, `BgMusicTrack`, `BgMusicAuthor` и sealed-класс
  `BgMusicSourceHint` с вариантом `TelegramPublic`.
- `BgMusicFormat.kt` — константы, лимиты, очистка текста (`sanitizeText` для однострочных полей и
  `sanitizeMultilineText` для описания), проверка имён записей и магических байтов.
- `BgMusicWriter.kt` — `write(manifest, cover, out)`. Все проверки и сборка JSON выполняются до первого
  байта в выходе, поэтому неверный вход не оставляет частичного файла. Порядок записей фиксирован, метки
  времени постоянны, поэтому результат детерминирован. Выходной поток не закрывается.
- `BgMusicReader.kt` — `read(input, declaredSize)` возвращает `Success`, `Unsupported` или
  `Invalid(reason)`. Исключения наружу не выходят, кроме `CancellationException`, которое пробрасывается.
  `looksLikeCandidate(fileName, mimeType)` даёт только подсказку.
- `BgMusicStrictJson.kt` — проверка строгого JSON перед разбором: грамматика RFC 8259, глубина вложенности,
  повторяющиеся ключи (раздел 11, пункт 5).
- `BgMusicImportDecision.kt` — `decide(playlistId, revision, existing)`.

Тесты: `app/src/test/java/com/beykus/beygram/data/music/bgmusic/`. В том числе 1500 детерминированных
входов для фаззинга (случайные байты, мутации архивов и мутации JSON). Каждый вход обязан дать результат,
без исключения.
