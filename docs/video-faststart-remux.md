# Fast-start MP4 без перекодирования: исследование (#1179)

Цель: перенести `moov` в начало MP4, чтобы файл можно было читать последовательно (и стримить) без потери качества.
Связано с #1179/#1121. Реализация не начата — это исследование возможностей текущих Media3/Android API.

## Зачем

`supports_streaming` в TDLib и `Mp4StreamingProbe` требуют, чтобы индекс (`moov`) шёл до медиаданных (`mdat`). Файлы
с `moov` в конце нельзя играть до полной загрузки: без индекса неизвестны смещения сэмплов. Это подтверждено
разбором TDLib в `docs/video-progressive-playback.md`.

Fast-start нужен в двух местах:

1. **Исходящие файлы** — чтобы получатель мог начать просмотр до полной загрузки, а `supports_streaming` был честным.
   Наши сжатые видео идут через muxer Media3, который *пытается* писать streamable output, но не гарантирует.
2. **Локальные входящие файлы** — не нужно, если реализован range-aware DataSource (#1179): он читает индекс из конца
   через `GetFileDownloadedPrefixSize` + `DownloadFile(offset, limit)`. Перепаковка входящих файлов была бы лишней
   тратой диска и времени.

## Что доступно сегодня (проверено по артефактам проекта)

| Вариант | Наличие | Перекодирование | Стоимость |
| --- | --- | --- | --- |
| `androidx.media3.muxer.Mp4Muxer` (медиа3-muxer 1.11.1) | **уже в classpath** (транзитивно через `media3-transformer`) | нет, копирование сэмплов | полная копия файла |
| `Transformer` + `DefaultMuxer`/`InAppMp4Muxer` | есть (`media3-transformer`) | transmux, если нет эффектов; иначе перекодирование | полная копия |
| `MediaMuxer` (Android framework) | есть | нет | **moov всегда в конце**, для fast-start не годится |
| `ffmpeg`/нативная библиотека | нет | — | запрещено без согласования (тяжёлая зависимость) |
| Чистый Kotlin: переписать боксы и поправить `stco`/`co64` | возможно | нет | полная копия (сдвиг `mdat`) |

### Mp4Muxer: подтверждённый API

Из `media3-muxer-1.11.1-sources.jar`:

```java
Mp4Muxer.Builder.setAttemptStreamableOutputEnabled(boolean)  // по умолчанию true
Mp4Muxer.Builder.setSampleCopyingEnabled(boolean)
int  addTrack(Format format)
void writeSampleData(int trackId, ByteBuffer data, BufferInfo info)
void addMetadataEntry(Metadata.Entry entry)
void close()
```

`InAppMp4Muxer` (путь Transformer) создаёт `Mp4Muxer` с `setAttemptStreamableOutputEnabled(true)` по умолчанию —
поэтому сжатые BeyGram видео обычно fast-start, но документация прямо оговаривает: «does not guarantee a streamable
MP4 output». Проверять конкретный файл нужно `Mp4StreamingProbe`.

### Почему не чистый Kotlin-сдвиг боксов

Технически возможно: разобрать верхнеуровневые боксы, записать `ftyp + moov + free` и скопировать `mdat`, добавив к
каждому смещению в `stco` (32-бит) или `co64` дельту. Риски:

- `stco` может переполниться при сдвиге → нужен переход на `co64` (переупаковка таблицы), это уже не «правка на месте»;
- фрагментированный MP4 (`moof`) и файлы с несколькими `moov` требуют отдельной логики;
- ошибка в смещениях делает файл невоспроизводимым, а проверить это можно только плеером;
- выигрыша в I/O нет: `mdat` всё равно копируется в новый файл.

`Mp4Muxer` делает то же самое, но проверенным кодом Media3, без своей реализации таблиц смещений.

## Предлагаемая архитектура

```
Mp4FastStartRemuxer(
  probe: Mp4StreamingProbe,          // уже есть: определяет moov после mdat
  muxerFactory = Mp4Muxer.Builder(...).setAttemptStreamableOutputEnabled(true),
  extractor = Mp4Extractor / MediaExtractor
)
```

1. Проверка: MP4, `moov` после `mdat`, размер ≤ порога (например, 500 МБ), на диске есть место под копию.
2. Ограниченный набор дорожек: `MediaExtractor.getTrackFormat()` возвращает платформенный `MediaFormat`, а
   `Mp4Muxer.addTrack()` принимает Media3 `Format` — это разные типы, их нужно явно конвертировать. Первый сценарий
   ограничен подтверждёнными типами (`video/avc`, `audio/mp4a-latm`); всё остальное сразу идёт в fallback.
3. Копирование: `MediaExtractor` отдаёт сэмплы, `Mp4Muxer.writeSampleData` их пишет. Декодирование не требуется.
   `addMetadataEntry` — не общий перенос MP4-боксов, а узкий набор поддерживаемых `Metadata.Entry`; поворот
   переносится через `Format.rotationDegrees`, остальные метаданные не гарантируются.
4. Проверка результата: совпадают количество дорожек, их типы и длительность; `Mp4StreamingProbe.inspect(output)
   .indexStreamable == true`; размер в разумных пределах; файл воспроизводится. Любое расхождение — удалить копию и
   отправить оригинал.
5. Использовать только когда файл реально уходит как видео и `moov` в конце. При отмене вложения — удалить временный
   файл.

Ограничения:

- полная копия файла: время и диск пропорциональны размеру; на больших видео это заметно, поэтому нужен порог и
  прогресс;
- не помогает входящим файлам — для них только range-aware DataSource;
- не менять BG Media и не добавлять нативные зависимости.

## Альтернатива без нового кода

Оставить как есть и полагаться на `attemptStreamableOutputEnabled = true` у Transformer: для сжатых видео этого
может быть достаточно, а для «оригинала» — нет. Тогда честный `supports_streaming = false` остаётся, и получатель
скачивает файл целиком. Это допустимый, но худший для пользователя вариант.

## Что нужно проверить на устройстве

1. Взять сжатое BeyGram видео и прогнать `Mp4StreamingProbe.inspect` — понять, действительно ли muxer пишет `moov`
   вперёд (гипотеза H2 из `docs/video-progressive-playback.md`).
2. Взять видео с `moov` в конце, перепаковать прототипом и проверить: играет, размер, `indexStreamable`, начало
   воспроизведения до полной загрузки у получателя.
3. Замерить время перепаковки на 50–100 МБ на M21.

## Вывод

Fast-start без перекодирования реализуем **на уже подключённых Media3-артефактах** (`Mp4Muxer` 1.11.1), без нативных
зависимостей и без потери качества, ценой полной копии файла. Приоритет — ниже range-aware DataSource: он решает
проблему просмотра входящих видео, тогда как перепаковка улучшает только исходящие. Реализацию предлагается делать
отдельным PR после подтверждения H2 на устройстве.
