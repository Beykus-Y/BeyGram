# TDLib reproducibility record

Issue: [#1129](https://github.com/Beykus-Y/BeyGram/issues/1129).

This document records what can be proven about the TDLib build shipped in BeyGram, what was
inferred, and what stays unknown. It does **not** update TDLib, replace binaries, change JNI, or
change client behaviour. The goal is that the next rebuild is a deliberate, repeatable operation
instead of an undocumented download.

Machine-readable copy: [`docs/tdlib-artifacts.json`](tdlib-artifacts.json).
Read-only check of the current checkout: `powershell -File scripts/verify-tdlib-artifacts.ps1 -InspectBinaries`.

Evidence marks used below:

| Mark | Meaning |
| --- | --- |
| **Confirmed** | Read directly from the committed artifacts, upstream sources or Git metadata. |
| **Derived** | Conclusion from confirmed facts plus documented upstream build logic. |
| **Assumption** | Plausible but not proven by evidence in this repository. |
| **Unknown** | Not recoverable without a rebuild or an owner-side device check. |

## 3. Confirmed API surface of the Java bindings

`tdlib-java.jar` contains 3 547 classes, of which 3 329 are `TdApi` API types. The set was compared
against upstream `td/generate/scheme/td_api.tl` snapshots:

| Upstream commit | Date | API entries absent from the jar |
| --- | --- | --- |
| `a8f21f523017` — "Update version to 1.8.65." | 2026-06-11 | 1 (`Bool`, a pseudo-type that upstream never generates as a class; the jar has no such class by design) |
| `a17f87c4cff7` — "Fix typos in API scheme docs" | 2026-06-13 | same |
| `14e281baca2e` — "Add td_api::inputRichMessageMedia" | 2026-06-15 | 2 (`InputRichMessageMedia` is missing) |
| `a9966eb3704a` — "Update version to 1.8.66." | 2026-07-14 | 63 |

**Derived:** the bindings were generated from a schema whose constructor set equals
`td_api.tl` at `a17f87c4cff7`, and the source snapshot lies in the open interval
`[a8f21f523017, 14e281baca2e)` — i.e. between 2026-06-11 and 2026-06-15.

**Unknown:** the exact commit inside that interval, and whether any *field* (not constructor) of the
schema differs from `a17f87c4cff7`. The comparison is constructor-level; a field-only change cannot
be detected this way.

Upstream has no `v1.8.65` Git tag — TDLib only tags `v1.8.0` and older — so "1.8.65" identifies a
version string, not a tag. Any future rebuild must pin a commit, not the string.

Repository-side wrappers that were used (**Confirmed** by their existence and by `docs/tdlib.md`):

- `scripts/build-tdlib.sh` — clones nothing, expects a prepared `td-master`, sets `TDLIB_GPERF_DIR`,
  `TDLIB_PHP_DIR`, `TDLIB_PERL_LIB`, `JAVA_HOME`, generates clang wrappers, then calls the upstream
  script with `OPENSSL_VERSION=openssl-3.3.0`.
- `scripts/install-tdlib.ps1` — compiles the generated `TdApi.java`/`Client.java` into
  `app/libs/tdlib-java.jar` and copies `libtd*.so` into `app/src/main/jniLibs/<abi>`.

## 5. Assumptions (explicitly not proven)

1. The native library was produced by `scripts/build-tdlib.sh` as committed, not by an ad-hoc command
   line. Supporting evidence: build path under `/mnt/f/BeyGram`, OpenSSL 3.3.0 (the script default),
   stripped output.
2. The build ran on a Windows host through WSL or Git Bash with the NDK installed under
   `C:\Users\Beykus\AppData\Local\Android\Sdk`, because `/mnt/f/...` and an Android SDK path are the
   only paths present.
3. `-DTD_GENERATE_SOURCE_FILES=ON` was configured in the same directory that then produced the
   bindings — i.e. bindings and native library come from one source snapshot. Nothing in the binary
   contradicts this, and both artifacts agree on the 1.8.65 schema.
4. No custom `-DCMAKE_CXX_FLAGS` were appended. The `.comment` section and inlined code show plain
   upstream release flags; nothing suggests `-flto` or `-fno-exceptions`.

## 6. Known gaps

| Gap | Why it matters | How to close it |
| --- | --- | --- |
| Exact upstream commit SHA | A rebuild cannot be proven identical without it | Rebuild from a pinned commit inside the interval and compare the API type set; the SHA is otherwise unrecoverable |
| NDK mismatch with the build scripts | `app/build.gradle.kts` uses `ndkVersion = "30.0.15729638"` and `scripts/build-tdlib.sh` defaults to the same NDK, but the shipped library was linked by NDK `r27d`. A rebuild with the committed defaults produces a *different* toolchain than the shipped binary. | Decide which NDK is authoritative before the next rebuild (owner decision, see §9) |
| Two different OpenSSL builds in the tree | `scripts/build-openssl-android.sh` builds OpenSSL **3.5.9 / API 29** for the BG Wave/WebRTC adapter and is unrelated to TDLib. Only `openssl-3.3.0` belongs to TDLib. | Keep the two documented separately; never point TDLib at the BG Wave prefix |
| `MTPROTO_LAYER` | Not extracted; it changes per release and pins the protocol layer | Read it from the device during the check in §7, or from a rebuild |
| Field-level schema identity | Constructor comparison cannot see field additions | Compare generated `TdApi.java` field lists after a rebuild |

### 6.1 OpenSSL 3.3.0 security assessment (read-only)

The statically linked OpenSSL predates the security fixes that landed in the 3.3.x series after 3.3.0.
The table below records each advisory from the audit and whether the affected API is plausibly reachable
from BeyGram's use of TDLib. This is a code-level triage, not a proof of exploitability: no fuzzing or
device-side attack was performed, and the upstream advisories remain authoritative.

| Advisory | Affected area | Plausible exposure in BeyGram |
| --- | --- | --- |
| CVE-2024-4603 | Excessive time checking DSA/DH parameters supplied by the peer | Low: a TLS client negotiates ECDHE named groups; DSA/DH parameter checks are not on the normal Telegram DC handshake |
| CVE-2024-4741 | Use-after-free in `SSL_free_buffers` | Low: TDLib's TLS wrapper does not expose `SSL_free_buffers` to application input |
| CVE-2024-5535 | Buffer overread in `SSL_select_next_proto` | Low: selected ALPN is fixed by the client; no peer-controlled protocol list is passed to that helper |
| CVE-2024-6119 | Denial of service while checking X.509 names | Low–medium: Telegram DC certificates are verified by TDLib's own pinned-key path; even a crafted chain is a DoS, not code execution |
| CVE-2024-9143 | Out-of-bounds access with invalid GF(2^m) curve parameters | Low: only named curves are used; explicit invalid parameters are not accepted from the peer |

**Conclusion.** No remote code-execution path through these advisories is demonstrated for this client.
The correct action is still a rebuild against a current, pinned OpenSSL 3.x release together with a
pinned TDLib commit (sections 9–10), not a local binary swap. Advisories published after this record
must be added to the same table in the next rebuild PR.

## 7. Device verification (read-only)

Nothing here writes to the device, opens the TDLib database, or touches the account. Run it only with
owner consent, and only for the package actually installed.

### 7.1 Which binary is really installed

```powershell
$adb = 'C:\Users\Beykus\AppData\Local\Android\Sdk\platform-tools\adb.exe'
$pkg = 'com.beykus.beygram.dev'                 # or com.beykus.beygram
& $adb shell dumpsys package $pkg | Select-String -Pattern 'versionName|versionCode|primaryCpuAbi'
& $adb shell pm path $pkg
& $adb pull <base.apk from the previous command> $env:TEMP\beygram-device.apk
```

Extract the library from the APK and compare hashes:

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip = [System.IO.Compression.ZipFile]::OpenRead("$env:TEMP\beygram-device.apk")
$entry = $zip.Entries | Where-Object { $_.FullName -eq 'lib/arm64-v8a/libtdjni.so' }
[System.IO.Compression.ZipFileExtensions]::ExtractToFile($entry, "$env:TEMP\libtdjni-device.so", $true)
$zip.Dispose()
(Get-FileHash "$env:TEMP\libtdjni-device.so" -Algorithm SHA256).Hash
```

The hash must equal
`a46c2d3ee2e9739197d5130b335858973e71d1d305870b94312fed94a7dc40fd`.
`libjniLibs` uses `useLegacyPackaging = true`, so the entry is stored uncompressed and the hash of the
packaged file equals the hash of the repository file. This is the only read-only way to prove that the
device runs the recorded binary.

### 7.2 `GetOption("version")` and `GetOption("commit_hash")`

The app does not query these options today, and this task deliberately adds no diagnostic code
(see §8). Expected values for the recorded artifacts, if queried:

- `version` → `1.8.65` (derived from the observed binary literal plus upstream behaviour; not yet observed)
- `commit_hash` → `GITDIR-NOTFOUND` (same: derived, not yet observed)

If an owner-side check is wanted, the smallest possible probe is a temporary, **not committed**,
debug-only call from an existing repository coroutine:

```kotlin
// Temporary local probe. Do not commit.
val version = (request(TdApi.GetOption("version")) as? TdApi.OptionValueString)?.value
val commit = (request(TdApi.GetOption("commit_hash")) as? TdApi.OptionValueString)?.value
android.util.Log.i("TdLibProbe", "version=$version commit=$commit")
```

Both options are synchronous in TDLib (`OptionManager::get_synchronous_options`), so the call returns
without network I/O and without touching authorization or the database. Reading the values through
`adb logcat -s TdLibProbe` requires a debug build; a release build logs at verbosity 0.

## 8. Why no diagnostic code was added

The issue requires the values "if possible" and forbids unnecessary diagnostic code. The version
literal and the `GITDIR-NOTFOUND` value are already inside the shipped binary, so a code change would
only re-read data that §1–§2 already establish, while touching the diagnostics screen that other work
depends on. The read-only APK hash check in §7.1 proves the same thing without modifying the client.

## 9. Decisions required from the owner

1. **Authoritative NDK for the next rebuild**: the shipped binary used NDK `r27d` (13750724); the
   committed scripts default to `30.0.15729638`. Pick one before the next rebuild and update both
   `app/build.gradle.kts` and `scripts/build-tdlib.sh`, or record the exception.
2. **Reproducibility target**: bit-identical output requires the same absolute source path, because
   `/mnt/f/BeyGram/td-master` is compiled into the binary. Choose either "same path" (strict) or
   "same commit, API set and behaviour" (practical).
3. **Whether to pin a commit**: since `commit_hash` was never embedded, the next rebuild should pass
   `-DTD_GIT_COMMIT_HASH=<sha>` so the value stops being `GITDIR-NOTFOUND`.

## 10. Rebuild procedure (not executed here)

Do not run this while an update of TDLib is not approved. It is documentation of a reproducible path,
not an invitation to change the library.

```bash
# 1. Pin sources: the schema commit established in §3.
mkdir -p /mnt/f/BeyGram/td-master
git clone https://github.com/tdlib/td /mnt/f/BeyGram/td-master
cd /mnt/f/BeyGram/td-master && git checkout a17f87c4cff7

# 2. Toolchain: NDK r27d = 27.3.13750724, CMake 3.22.1, OpenSSL 3.3.0, gperf, php, make, JDK.
#    scripts/build-tdlib.sh requires TDLIB_GPERF_DIR, TDLIB_PHP_DIR, TDLIB_PERL_LIB, JAVA_HOME.
./scripts/build-tdlib.sh /mnt/c/Users/Beykus/AppData/Local/Android/Sdk 27.3.13750724
```

Then install and verify:

```powershell
.\scripts\install-tdlib.ps1 -TdLibOutput .\td-master\example\android\tdlib
powershell -File scripts\verify-tdlib-artifacts.ps1 -InspectBinaries
```

The verify script fails when the artifacts no longer match the record. That failure is the signal to
update `docs/tdlib-artifacts.json` deliberately, together with a device check, and never as a side
effect of an unrelated build.
