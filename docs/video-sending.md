# Видео: отправка, сжатие и стриминг — три разные возможности (#1175)

Документ фиксирует, что именно решает приложение при отправке видео и почему эти решения нельзя связывать одним
условием. Связано с Issue #1175 и #1121.

## Контракт TDLib (1.8.65, проверено по `td_api.tl` и `tdlib-java.jar`)

- `inputVideo` принимает файл без ограничения по кодеку. Документация: «The video is expected to be re-encoded to
  MPEG4 format with H.264 codec by the sender» — это рекомендация отправителю, а не требование API.
- `supports_streaming` — «True, if the video is expected to be streamed»: подсказка о том, что файл можно читать
  постепенно. Она описывает **раскладку контейнера** (`moov` перед `mdat`), а не кодек.
- `DownloadFile(fileId, priority, offset, limit, synchronous)` — диапазонная загрузка.
- `LocalFile` содержит `downloadOffset`, `downloadedPrefixSize`, `downloadedSize`; доступность произвольного
  диапазона даёт отдельный запрос `GetFileDownloadedPrefixSize(fileId, offset)` (см. `docs/video-progressive-playback.md`).

## Три независимых решения

| Возможность | Где решается | От чего зависит |
| --- | --- | --- |
| Отправить как видео-сообщение | `videoCanBeSentAsVideoMessage` (`VideoImportPolicy.kt`) | Контейнер `video/mp4` + кодек из подтверждённых (H.264, HEVC). |
| Сжать / перекодировать | `videoCompressionPlan` + `VideoCodecClass` | Кодек, метаданные, битрейт, размер, наличие декодера/энкодера. |
| Играть до полной загрузки | `Mp4StreamingProbe` | `moov` целиком и до `mdat`; для локального плеера ещё и поддерживаемый кодек. |

## Политика кодеков

| Кодек в MP4 | Класс | Отправка сразу как видео | Что делает композер |
| --- | --- | --- | --- |
| H.264 (`avc1`/`avc3`) | `Avc` | да | не перекодирует для совместимости, может сжать по размеру |
| HEVC (`hvc1`/`hev1`) | `Hevc` | да: Telegram Android сам кодирует HEVC, iOS декодирует нативно | может сжать по размеру |
| AV1 (`av01`), VP9 (`vp09`), MPEG-4 Part 2, смешанные дорожки | `Unconfirmed` | **нет** | предлагает перекодирование в H.264; после успеха вложение становится видео |
| MKV, WebM, MOV | — | нет | остаются документами |

`videoCanBeSentAsVideoMessage` возвращает `true` только для подтверждённых кодеков. Неподтверждённые не выдаются за
совместимые: файл импортируется документом, а в композере доступен выбор качества (`qualityKind()` возвращает
`Video` для `video/mp4`-документов). «Compact»/«Balanced» запускают перекодирование в H.264/AAC, и после него
`adoptCompressedVideo` возвращает `MediaKind.Video` — сообщение уходит видео.

**Fallback без перекодирования:** если выбрано «Оригинал», файл слишком长/велик, метаданные недоступны или
устройство не может перекодировать, вложение остаётся документом с исходными байтами и подсказкой
`composer_quality_hint_codec` («Кодек этого видео не поддерживается Telegram…»). Никакой потери файла и никаких
обещаний совместимости.

## Что было сломано до #1175

```kotlin
// было: возможность отправки зависела от кодека
mimeType == "video/mp4" && videoCodecs.isNotEmpty() && videoCodecs.all { it == "video/avc" }
```

Любой MP4 кроме H.264 становился `MediaKind.Document` ещё на импорте: композер не предлагал ни сжатие, ни
перекодирование. Именно поэтому HEVC-видео с телефона уходило файлом.

Дополнительно исходящий `supports_streaming` вычислялся по `streamable`, то есть требовал ещё и «понятный» кодек. Для
fast-start HEVC это давало `false`, хотя файл структурно пригоден для стриминга.

## Что изменено

1. `videoCodecClass` / `videoCanBeSentAsVideoMessage` — контейнер + подтверждённый кодек (H.264, HEVC).
2. `videoIsAlreadyTargetCodec`, `videoCodecNeedsConversion` — отдельные предикаты для планировщика сжатия и для
   перекодирования неподтверждённых кодеков.
3. `Mp4StreamingProbe.indexStreamable` — структурный факт; `streamable` по-прежнему требует поддерживаемого кодека.
4. `OutgoingMediaContent` пишет `supportsStreaming` из `supportsOutgoingStreaming`, то есть из структуры.
5. Композер: `qualityKind()` для `video/mp4`-документов, принудительное перекодирование неподтверждённого кодека
   (важнее эвристики «не стоит сжимать»), подсказка-объяснение при отказе.

## Что осталось как было

- MKV, WebM и MOV остаются документами.
- Пользователь может явно отправить видео файлом (`MediaDeliveryMode.File`).
- Сжатие не обещает успеха: при неудаче остаётся оригинал (документ для неподтверждённого кодека).
- Видео-заметки, BG Media и музыкальная подсистема не затронуты.

## Известное ограничение

HEVC отправляется видео и играет на актуальных клиентах Telegram, но на очень старых устройствах без HEVC-декодера
получатель увидит видео, которое не сможет воспроизвести. Это лучше документа: файл доставляется как видео и
открывается клиентами, которые кодек поддерживают.

## Проверка

```powershell
./gradlew :app:testDevDebugUnitTest --tests "com.beykus.beygram.data.media.*"
```

Тесты: `VideoImportPolicyTest` (H.264 и HEVC — видео; AV1/VP9/MPEG-4/mixed — не видео, но с перекодированием;
MKV/WebM/MOV — документы) и `Mp4StreamingProbeTest.outgoingStreamingFlagFollowsTheIndexNotTheCodec`.

На устройстве остаётся проверить фактическую доставку: HEVC — получателю с актуальным клиентом, AV1/VP9 — после
перекодирования в H.264. Это требует реальной отправки и согласия владельца.
