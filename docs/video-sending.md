# Видео: отправка, сжатие и стриминг — три разные возможности (#1175)

Документ фиксирует, что именно решает приложение при отправке видео. Связано с #1175 и #1121.

## Контракт TDLib (1.8.65, проверено по `td_api.tl` и `tdlib-java.jar`)

- `inputVideo` принимает файл; документация: «The video is expected to be re-encoded to MPEG4 format with H.264
  codec by the sender» — рекомендация отправителю.
- `supports_streaming` описывает раскладку контейнера (`moov` перед `mdat`), а не кодек.
- `DownloadFile(offset, limit)` и `GetFileDownloadedPrefixSize(fileId, offset)` дают диапазонную загрузку и проверку
  доступности конкретного смещения (см. `docs/video-progressive-playback.md`).

## Подтверждённая область совместимости — только H.264 в MP4

| Кодек в MP4 | Класс | Отправка сразу как видео | Что делает композер |
| --- | --- | --- | --- |
| H.264 (`avc1`/`avc3`) | `Avc` | да | не перекодирует для совместимости, может сжать по размеру |
| HEVC (`hvc1`/`hev1`) | `Hevc` | **нет** | перекодирование в H.264; после успеха вложение становится видео |
| AV1 (`av01`), VP9 (`vp09`), MPEG-4 Part 2, смешанные дорожки | `Unconfirmed` | **нет** | то же перекодирование |
| MKV, WebM, MOV | — | нет | остаются документами |

То, что один Android-клиент умеет кодировать HEVC, а iOS декодирует HEVC нативно, **не доказывает** воспроизведение
произвольного MP4/HEVC-профиля у получателя: профили, уровни и аппаратные декодеры различаются. Поэтому HEVC не
отправляется видео автоматически, а идёт тем же путём, что AV1/VP9: документ + перекодирование в H.264.

## Сценарий отказа (fallback)

Если перекодирование невозможно — нет декодера, превышен лимит размера или длительности, выбран «Оригинал» или кодер
вернул ошибку — файл остаётся документом с исходными байтами и подсказкой `composer_quality_hint_codec`
(«Кодек этого видео не поддерживается Telegram. Сожмите его, чтобы отправить как видео, или оставьте файлом»).
Никакой потери файла и никаких обещаний совместимости.

## Что было сломано до #1175

```kotlin
// было: возможность отправки зависела от кодека
mimeType == "video/mp4" && videoCodecs.isNotEmpty() && videoCodecs.all { it == "video/avc" }
```

Любой MP4 кроме H.264 становился `MediaKind.Document` ещё на импорте: композер не предлагал ни сжатие, ни
перекодирование, поэтому HEVC-видео с телефона уходило файлом без всякой альтернативы.

Дополнительно исходящий `supports_streaming` вычислялся по `streamable`, то есть требовал ещё и «понятный» кодек.

## Что изменено

1. `videoCodecClass` / `videoCanBeSentAsVideoMessage` — видео только для подтверждённого H.264.
2. `videoCodecNeedsConversion` — HEVC, AV1, VP9 и неизвестные кодеки получают явный путь перекодирования;
   `videoIsAlreadyTargetCodec` остаётся предикатом планировщика сжатия.
3. `Mp4StreamingProbe.indexStreamable` — структурный факт; `streamable` по-прежнему требует поддерживаемого кодека.
4. `OutgoingMediaContent` пишет `supportsStreaming` из структуры контейнера.
5. Композер: `qualityKind()` для `video/mp4`-документов, принудительное перекодирование (важнее эвристики «не стоит
   сжимать»), подсказка-объяснение при отказе.

## Что осталось как было

- MKV, WebM и MOV остаются документами.
- Пользователь может явно отправить видео файлом (`MediaDeliveryMode.File`).
- Видео-заметки, BG Media и музыкальная подсистема не затронуты.

## Проверка

```powershell
./gradlew :app:testDevDebugUnitTest --tests "com.beykus.beygram.data.media.*"
```

Тесты: `VideoImportPolicyTest` (H.264 — видео; HEVC/AV1/VP9/MPEG-4/mixed — документ + `videoCodecNeedsConversion`;
MKV/WebM/MOV — документы), `AttachmentComposerTest` (перекодированный документ уходит видео, «Оригинал» сохраняет
документ), `OutgoingVideoStreamingFlagTest` (`supports_streaming` по структуре, не по кодеку).

На устройстве остаётся проверить фактическую отправку: H.264 — как раньше, HEVC/AV1/VP9 — после перекодирования, и
что при отказе кодера файл уходит документом. Это требует реальной отправки и согласия владельца.
