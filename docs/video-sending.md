# Видео: отправка, сжатие и стриминг — три разные возможности (#1175)

Документ фиксирует, что именно решает приложение при отправке видео, и почему эти решения нельзя связывать одним
условием. Связано с Issue #1175 и #1121.

## Контракт TDLib (1.8.65, проверено по `td_api.tl` и `tdlib-java.jar`)

- `inputVideo` принимает файл без ограничения по кодеку. Документация: «The video is expected to be re-encoded to
  MPEG4 format with H.264 codec by the sender» — это рекомендация отправителю, а не требование API.
- `supports_streaming` — «True, if the video is expected to be streamed»: подсказка о том, что файл можно читать
  постепенно. Она описывает **раскладку контейнера** (`moov` перед `mdat`), а не кодек.
- В `LocalFile` этой версии есть только `downloadOffset`, `downloadedPrefixSize`, `downloadedSize`. Поля для
  скачанного «хвоста» нет, поэтому забрать `moov` из конца недокачанного файла нельзя (важно для #1121).
- `DownloadFile(fileId, priority, offset, limit, synchronous)` — диапазонная загрузка есть, но без отчётности о
  суффиксе в `LocalFile`.

## Три независимых решения

| Возможность | Где решается | От чего зависит |
| --- | --- | --- |
| Отправить как видео-сообщение | `videoCanBeSentAsVideoMessage` (`VideoImportPolicy.kt`) | Контейнер `video/mp4` + наличие видеодорожки. Кодек не важен. |
| Сжать локально | `videoCompressionPlan` (`VideoCompressionPolicy.kt`) + `VideoCompressor` | Метаданные, кодек (`videoIsAlreadyTargetCodec`), битрейт, размер, наличие декодера/энкодера на устройстве. |
| Играть до полной загрузки | `Mp4StreamingProbe` | `moov` целиком и до `mdat`; для локального плеера ещё и кодек из списка поддерживаемых. |

## Что было сломано

До #1175 первое решение зависело от второго:

```kotlin
// было
mimeType == "video/mp4" && videoCodecs.isNotEmpty() && videoCodecs.all { it == "video/avc" }
```

MP4 с HEVC/AV1/VP9 становился `MediaKind.Document` ещё на импорте: композер не предлагал ни «сжать», ни «отправить
оригиналом», получатель видел файл, а прогрессивное воспроизведение было недоступно в принципе.

Кроме того, исходящий `supports_streaming` вычислялся по `streamable`, то есть требовал ещё и «понятный» кодек. Для
fast-start HEVC это давало `false`, хотя файл структурно пригоден для стриминга.

## Что изменено

1. `videoCanBeSentAsVideoMessage(mimeType, videoCodecs)` — контейнер `video/mp4` + непустой список видеодорожек.
   Кодек больше не участвует.
2. `videoIsAlreadyTargetCodec(videoCodecs)` — отдельный предикат для планировщика сжатия (H.264 = `video/avc`).
3. `Mp4StreamingProbe.indexStreamable` — структурный факт (полный `moov`, перед `mdat`, в пределах лимитов).
   `Mp4StreamingProbe.streamable` по-прежнему означает «этот плеер сможет это играть» и требует поддерживаемого кодека.
4. `OutgoingMediaContent` пишет `supportsStreaming` из `supportsOutgoingStreaming`, то есть из структуры.

## Что осталось как было

- MKV, WebM и MOV остаются документами: их поведение как видео-сообщения в Telegram не подтверждено, а менять его
  без проверки нельзя.
- Пользователь по-прежнему может явно отправить видео файлом (`MediaDeliveryMode.File`).
- Сжатие не обещает успеха: при невозможности перекодировать файл отправляется оригинал, тип сообщения не меняется.
- Видео-заметки, BG Media и музыкальная подсистема не затронуты.

## Совместимость кодеков: что проверено, а что нет

| Кодек в MP4 | TDLib принимает как видео | Воспроизведение у получателя |
| --- | --- | --- |
| H.264 (`avc1`/`avc3`) | да | да, целевой кодек Telegram |
| HEVC (`hvc1`/`hev1`) | да, API не валидирует кодек | да: Telegram Android умеет **кодировать** HEVC (`MediaController`, `MediaCodec.createEncoderByType("video/hevc")`), iOS декодирует его нативно |
| AV1 (`av01`) | да | не подтверждено: в исходниках Telegram Android нет упоминаний AV1, у iOS нет декодера |
| VP9 (`vp09`) | да | не подтверждено: в Telegram Android нет упоминаний VP9 |
| MPEG-4 Part 2 (`mp4v`) | да | не подтверждено |

Важное разделение: **TDLib не проверяет кодек** — `inputVideo` принимает файл, а сервер сохраняет атрибуты видео. Значит
«пройдёт ли отправка» не зависит от кодека; зависит только воспроизведение на конкретном клиенте получателя.
Проверить доставку и воспроизведение AV1/VP9 можно только реальной отправкой — в этой задаче она не выполнялась.

Практический вывод: HEVC — основной исправленный случай (именно он приходил документом). Для AV1/VP9 файл тоже
становится видео-сообщением, но максимальную совместимость даёт сжатие в H.264: композер предлагает «Compact» и
«Balanced», а `VideoCompressor` перекодирует в H.264/AAC. Если сжатие не удалось, отправляется оригинал — с тем же
типом сообщения, без потери файла.

## Известное ограничение

Если MP4 содержит кодек, которого нет на устройстве (например, MJPEG в MP4), сообщение всё равно уходит видео, но
встроенный плеер может показать ошибку декодирования. Это осознанный обмен: раньше такой файл уходил документом и
терял видео-представление у всех получателей, теперь он доставляется как видео, а открыть его можно любым клиентом,
который кодек поддерживает.

## Проверка

```powershell
./gradlew :app:testDevDebugUnitTest --tests "com.beykus.beygram.data.media.*"
```

Тесты: `VideoImportPolicyTest` (MP4 + HEVC/AV1/VP9 = видео; MKV/WebM/MOV = документ; пустой список дорожек =
документ; H.264-предикат) и `Mp4StreamingProbeTest.outgoingStreamingFlagFollowsTheIndexNotTheCodec`.

На устройстве остаётся проверить только фактическую доставку HEVC-видео получателю — это требует реальной отправки
и согласия владельца.
