# Почему видео ждёт полной загрузки (#1121, продолжение)

Исследование по ручному отчёту: в DEV 697 видео начинает играть только после полного скачивания. Ниже — что
проверено по коду и исходникам, что этим объясняется, а что требует устройства. Замеров нет: прирост не заявляется.

## Как сейчас устроено воспроизведение

`MediaViews.kt` (DEV `9093fa00`), просмотрщик медиа:

1. Пока открыта страница, приложение просит `DownloadFile(fileId)` (приоритет 16).
2. `Mp4StreamingProbe.inspect(File(downloadPath), downloadedPrefixBytes)` читает только заголовки боксов и `moov`
   из уже скачанного префикса.
3. Если `streamable == true`, создаётся `ProgressiveVideoSource` и ExoPlayer читает растущий файл через
   `ProgressiveFileDataSource` (`readablePrefix = downloadedPrefixSize`).
4. Иначе остаётся ветка `path == null`: спиннер и текст «скачано X из Y», то есть воспроизведение после полной
   загрузки.

Значит вопрос «почему ждёт полной загрузки» = «почему шаг 3 не срабатывает или срывается».

## Решение пробника: какие причины постоянные

`Mp4StreamingProbe` возвращает одну из причин. `MediaViews` помечает страницу как окончательно не стримящуюся
(`progressiveRejected`) только для:

| Причина | Постоянная | Что означает |
| --- | --- | --- |
| `NotMp4` | да | контейнер не MP4 |
| `MoovAfterMediaData` | да | `moov` после `mdat`: без полного файла индекс не прочитать |
| `MoovTooLarge` | да | `moov` больше 16 МБ, индексу не доверяем |
| `NoVideoTrack` | да | видеодорожки нет |
| `UnsupportedVideoCodec` | да | кодек вне списка `avc1/hvc1/hev1/vp09/av01/mp4v` |

`MissingMoov` и `TruncatedMoov` **не** постоянные: эффект перезапускается при росте `downloadedPrefixSize`, поэтому
медленный старт сам по себе не блокирует стриминг навсегда.

## Проверенные факты

1. **TDLib 1.8.65 не умеет сообщать о скачанном «хвосте».** `TdApi.LocalFile` содержит только `downloadOffset`,
   `downloadedPrefixSize`, `downloadedSize` (проверено `javap` по `app/libs/tdlib-java.jar`). `DownloadFile` умеет
   `offset/limit`, но без отчётности о суффиксе нельзя надёжно забрать `moov` из конца файла. Вывод: для файлов с
   `moov` в конце прогрессивное воспроизведение в этой версии TDLib невозможно — только полная загрузка.
2. **Media3 1.11.1 по умолчанию пытается писать streamable MP4.** `Transformer` использует `DefaultMuxer` →
   `InAppMp4Muxer.Factory`, у которого `attemptStreamableOutputEnabled = true` по умолчанию (исходники тега 1.11.1,
   `libraries/transformer/.../InAppMp4Muxer.java`, конструктор `Factory(MetadataProvider)`). Документация тут же
   оговаривает: «Setting to true does not guarantee a streamable MP4 output». То есть сжатые BeyGram видео обычно
   fast-start, но гарантии нет, и проверять нужно конкретный файл.
3. **Срыв стриминга выглядит как «ждёт полную загрузку».** `ProgressiveFileDataSource` бросает `IOException` после
   45 с ожидания очередного чанка (`STALL_TIMEOUT_MS`) и после 10 с, если загрузка не активна
   (`NO_TRANSFER_TIMEOUT_MS`). Ошибка плеера возвращает страницу к ветке полной загрузки, и пользователь видит
   именно «скачивается целиком».
4. **Один приоритет загрузки на все случаи.** `TdLibTelegramRepository.sendDownload` всегда использует
   `DownloadFile(fileId, priority = 16, ...)`. У TDLib приоритет 32 означает «скачать как можно скорее»; для
   файла, который пользователь уже открыл, 16 может уступать другим загрузкам и давать ровно тот stall из п. 3.

## Гипотезы (не подтверждены без устройства)

| # | Гипотеза | Как проверить |
| --- | --- | --- |
| H1 | Файл не fast-start (`moov` в конце) — типично для видео, отправленных другими клиентами как документ или записанных приложениями без оптимизации | `Mp4StreamingProbe.inspect` на локальном файле: причина `MoovAfterMediaData` |
| H2 | Сжатые BeyGram видео иногда не fast-start, потому что muxer лишь «пытается» зарезервировать место | прогнать `inspect` на выходе `VideoCompressor` |
| H3 | Префикс скачивается медленно из-за приоритета 16, стриминг срывается по таймауту | залогировать `downloadedPrefixSize` во времени и причину срыва |
| H4 | Конкретный файл имеет редкий кодек → `UnsupportedVideoCodec` | `inspect` даёт эту причину |

H1 объясняет поведение полностью и не является ошибкой кода: без индекса в начале играть нельзя.

## Что предлагается делать

1. **Диагностика причины** — уже реализуется отдельно: PR #1176 (`claude/progressive-diag-1174`,
   `ProgressiveAttemptDiagnostics`) пишет `video_progressive_attempt` с причиной пробы, раскладкой боксов, размером
   префикса и таймингами чтения. Этот документ такую диагностику **не дублирует** и не добавляет своих событий.
   После интеграции #1176 отчёт владельца сразу покажет `cause` (`moov_at_end`, `prefix_too_small`, `codec_unsupported`,
   `probe_starved`, `offset_nonzero`).
2. **Приоритет 32 для открытого пользователем файла**: приоритет — параметр `sendDownload`, значение 32 только для
   действия «я открыл это видео/файл», остальные остаются 16. Требует проверки на устройстве, что не голодают
   остальные загрузки.
3. **Fast-start при отправке оригинала**: если файл уходит как видео, но `moov` в конце, его можно перепаковать
   локально до загрузки (тот же `Mp4StreamingProbe` уже умеет определять случай). Это отдельная задача: перепаковка
   без перекодирования.
4. **Не пытаться качать хвост**: в 1.8.65 нет отчётности о суффиксе; обновление TDLib не входит в эту задачу.

## Совместимость с PR #1176 и #1178

- #1176 и #1178 меняют `Mp4StreamingProbe.kt`, но в разных местах: #1176 добавляет `Mp4Layout`/`topLayout()` для
  диагностики, #1178 — поле `indexStreamable` и `supportsOutgoingStreaming()`. `git merge-tree --write-tree` для
  этих двух веток завершается успешно (exit 0), текстовых конфликтов нет.
- Диагностика прогрессивных попыток — только в #1176. Здесь её нет.

## Что нужно от устройства

1. Найти видео, которое не начинает играть до полной загрузки.
2. В debug-сборке посмотреть причину пробника и `downloadedPrefixSize` в момент открытия страницы.
3. Сравнить с `inspect` на уже скачанном файле: если после полной загрузки причина `Streamable`, значит стриминг
   сорвался по таймауту (H3), а не из-за структуры (H1).

Только после этого имеет смысл менять `LoadControl`, приоритеты или добавлять перепаковку. Ни одно из этих
изменений не заявляется как ускорение без замеров.
