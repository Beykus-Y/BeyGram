# Ручные обновления Stable

BeyGram Stable (`com.beykus.beygram`) проверяет публичные GitHub Releases **только после нажатия**
«Настройки → Обновления → Проверить обновления». Никаких WorkManager, фоновых запросов,
автоматического скачивания или принудительной установки нет. DEV (`com.beykus.beygram.dev`)
использует тот же экран и ту же логику по своему каналу (см. раздел «DEV-канал»).

## Публикация Stable-релиза и changelog

1. В PR, который готовит следующую Stable-версию, обновить
   `release-version.properties` (например, до `0.0.0.7`) **и в том же PR**
   добавить человекочитаемый `docs/releases/v0.0.0.7.md`.
   Формат и шаблон: [docs/releases/README.md](releases/README.md).
   Русский текст описывает только проверенные изменения этой Stable-версии.
   Валидация выполняется при изменении версии в PR и перед публикацией:

   ```bash
   python3 scripts/release_notes.py validate
   python3 -m unittest discover -s scripts -p 'test_*.py'
   ```

2. Gradle вычисляет Android `versionCode` по схеме
   `major*100000000 + minor*1000000 + patch*10000 + revision`.
   Допустимые компоненты: major 0–20, minor/patch 0–99, revision 0–9999;
   итог 1–2100000000. Проверить соответствие имени версии, versionCode,
   package name и ключа подписи перед релизом.

3. После успешного CI на **том же коммите `main`** опубликовать тег
   `v0.0.0.7` либо вручную запустить `Android release` из `main`
   с `publish=true` и точной версией. CI **не пересобирает** APK при
   публикации, а использует подписанный артефакт успешной сборки этого SHA.
   Отсутствие файла changelog, несовпадение версий и подписи останавливает
   публикацию.

4. Workflow автоматически дополняет русский текст техническим перечнем PR
   через GitHub Release Notes API (`.github/release.yml`); если GitHub API
   временно недоступен, ставится ссылка на коммит вместо выдуманных изменений.
   Служебный маркер `<!-- TECHNICAL_CHANGELOG -->` отделяет этот перечень:
   GitHub показывает всё, BeyGram в экране обновлений показывает только
   авторскую пользовательскую часть. На клиенте текст разбит на заголовки
   и пункты списка без выполнения HTML/Markdown в WebView.

5. Сначала создаётся **Draft** с описанием, затем загружаются и проверяются
   оба обязательных артефакта, и только после этого Draft публикуется
   (не появится преждевременно в GitHub Releases/latest). При частичном
   сбое можно безопасно повторить публикацию того же Draft. Уже **публичный**
   релиз не изменяется/не перезаписывается этим workflow.

6. Вместе с `BeyGram-0.0.0.7-prod-release.apk` публикуется
   `BeyGram-stable-update.json` вида (пример, реальные хеш и размер CI
   берёт из конкретного подписанного APK):

   ```json
   {
     "schema": 1,
     "versionName": "0.0.0.7",
     "versionCode": 7,
     "apkName": "BeyGram-0.0.0.7-prod-release.apk",
     "size": 70971042,
     "sha256": "<64 lowercase hex SHA-256 of the actual signed APK>"
   }
   ```

Выпуски до поддержки manifest (например, `v0.0.0.3`) не предлагаются
к установке. Для уже существующих опубликованных релизов новый workflow
не меняет APK и описание задним числом. Поскольку на момент внедрения
`release-version.properties` содержит `0.0.0.6`, публикация этой версии
с новым workflow тоже требует **реально составленного** файла
`docs/releases/v0.0.0.6.md`; заглушка автоматически не создаётся.

## Проверки на клиенте

GitHub Releases/latest → существует Stable APK и manifest → валидны версия, имя, размер и SHA-256 →
`versionCode > installedVersionCode` → **по отдельному нажатию пользователя** HTTPS-загрузка →
точный размер и хеш → проверка package name/версии/сертификата через PackageManager →
`FileProvider` → системное подтверждение установки Android → проверка установленного `versionCode`.

Не удаляйте текущий BeyGram при ошибке подписи: это удалит локальные данные и TDLib-сессию.
Разрешение «Установка неизвестных приложений» запрашивается только по нажатию «Разрешить установку».

## Состояния и координатор

Состояние обновлений держит процессный `UpdateCoordinator` (`data/update`), а не экран. Закрытие экрана
или поворот не останавливают загрузку. Экран только показывает состояние и отправляет действия.
Операции выполняются по одной: пока одна идёт, новая не запускается.

| Состояние | Что означает |
|---|---|
| `Checking` | Запрос к GitHub; ничего не скачивается |
| `Available` / `Current` | Новее ничего нет / есть новая версия |
| `Downloading(bytes, total, скорость, ETA)` | Байты приходят. Скорость сглаживается; ETA только после 3 с и 5 замеров. Обновления UI не чаще 4 раз в секунду |
| `Verifying` | Все байты получены, но SHA-256 и подпись ещё проверяются. **100 % ≠ проверено** |
| `Ready` | Файл проверен и сохранён. Установка доступна |
| `PreparingInstall` | Повторная проверка SHA-256, размера, пакета и подписи перед установщиком |
| `PermissionRequired` | Android не разрешает установку. Кнопка «Разрешить установку» открывает настройки, «Продолжить установку» запускает проверку снова |
| `AwaitingInstaller` | APK передан установщику Android через FileProvider |
| `Installed(versionCode)` | Установленный `versionCode` стал не ниже версии релиза |
| `Failure(шаг, причина, релиз)` | Понятный текст по типизированной причине |

Наличие успешного `startActivity` не считается установкой. Когда экран снова становится активным
(`ON_RESUME`), координатор читает установленный `versionCode`:
- если он не вырос, проверенный APK остаётся на месте и предлагается снова (`NotInstalledYet`);
- если вырос, состояние становится `Installed`, а APK больше не нужен.

Отказ в установщике тоже не удаляет проверенный APK.

## Докачка

Докачка возможна, только если выполнены все условия:

- сохранённая часть (`*-resume-<versionCode>-<sha256[:16]>.part`) относится к тому же релизу
  (`versionCode`, SHA-256, размер и имя APK совпадают);
- сервер сохранил сильный валидатор (ETag без `W/`, иначе Last-Modified);
- часть меньше размера APK и не старше 24 часов.

Запрос: `Range: bytes=N-` и `If-Range: <валидатор>`. Принимается только `206` с `Content-Range`, где
начало равно N, а полный размер равен ожидаемому. `200` означает «весь файл»: часть удаляется, загрузка с нуля.
`416` или несовпадающий `Content-Range`/валидатор: часть удаляется, файл запрашивается без диапазона.
Финальный SHA-256 считается по всему файлу, включая уже сохранённую часть, и проверка пакета и подписи
выполняется всегда.

- Временный обрыв сети: часть сохраняется; «Повторить загрузку» продолжает с места обрыва.
- Ошибка SHA-256, пакета, подписи или некорректные метаданные: часть удаляется, повторное использование невозможно.
- Явная отмена («Отменить загрузку»): сетевой вызов закрывается сразу, часть удаляется.
- После перезапуска процесса часть не считается работающей операцией; она проверяется при следующей загрузке.

## Хранение APK

Все файлы живут только в папке канала (`cache/stable-updates` или `cache/dev-updates`). Другие каталоги
(TDLib, медиа) никогда не затрагиваются.

- Каждая загрузка получает новое имя (`<канал>-<uuid>.apk`). Файл, переданный установщику, не перезаписывается.
- Защищены: готовый APK, APK, переданный установщику, и часть текущей загрузки.
- Очистка при запуске и перед загрузкой (`ApkRetentionPolicy`): сверх двух незащищённых `.apk` удаляются
  лишние, старше 7 дней удаляются тоже; `.part` старше 24 часов удаляются.
- Готовый APK при запуске проверяется заново (размер и SHA-256). Повреждённый файл не используется.

## Типизированные причины ошибок

`StableUpdateReason`: `Network`, `Timeout`, `RateLimited` (HTTP 403/429), `MissingRelease` (HTTP 404 и релиз без
APK), `MissingAsset`, `ServerError`, `InvalidMetadata`, `NoFreeSpace`, `AlreadyInstalled`, `Outdated`
(версия не новее установленной), `ChecksumMismatch`, `PackageMismatch`, `SignerMismatch`, `InstallerLaunch`,
`MissingFile`, `Storage` (нет доступа к папке или места для записи), `UntrustedRedirect` (перенаправление не на GitHub).
Каждая причина имеет собственный текст на экране; сырые тексты сервера и системы на экран не выводятся.
Ошибка проверки обновлений не удаляет уже проверенный готовый файл.

## DEV-канал

DEV (`com.beykus.beygram.dev`) берёт предрелизы `dev-N` с наибольшим N, манифест с закреплённым пакетом
и SHA-256 подписи. Тот же координатор, докачка и хранение. Старые DEV-APK больше не удаляются
при каждой загрузке: это делает общая политика хранения, которая не трогает переданный установщику APK.

## Mihomo fallback: рассмотрено и отклонено

Вариант «если прямой HTTPS к GitHub не работает, скачать через локальный прокси Mihomo» оценён и **не реализован**:

- загрузка пошла бы через локальный прокси, то есть появилась бы ещё одна точка доверия к TLS и к перенаправлениям;
- список разрешённых хостов перенаправлений (`github.com`, `api.github.com`, `release-assets.githubusercontent.com`,
  `objects.githubusercontent.com`) пришлось бы расширять или обходить для прокси;
- ошибки SHA-256 и подписи нельзя повторять через другой маршрут: такой повтор скрывал бы подмену файла.

Единственный маршрут обновлений: прямой HTTPS к GitHub. Ошибки сети показываются как «нет связи», без обхода.

## Ручной smoke-test на отдельном устройстве

- Подписанный Stable N установлен и залогинен. Обновить до N+1 через экран; сверить,
  что сессия Telegram, медиа и настройки сохранились.
- Установить последнюю версию: ручная проверка должна показать «актуальная версия».
- Проверить офлайн, отсутствие manifest, HTTP 403/429, обрыв загрузки, «Отменить»,
  недостаток места, несовпадение SHA-256 и чужую подпись — установщик не открывается.
- Проверить отказ в Android-разрешении, отказ в установщике, возврат в приложение и повтор.
- На **Android 10 (API 29, ARM64)** и на современном Android запустить
  `StableArchiveSigningAndroidTest` на изолированном эмуляторе/тестовом устройстве:
  проверяется реальное получение подписи архивного APK через тот же код, что использует updater.
  Если `GET_SIGNING_CERTIFICATES` не заполняет `signingInfo` на API 29,
  приложение безопасно переходит к `GET_SIGNATURES`; пустая или чужая подпись — отказ.
- Во время проверки SHA-256 перед установкой быстро нажать «Проверить обновления»,
  затем после открытия системного установщика снова открыть BeyGram и скачать обновление:
  файл, URI которого уже был передан установщику, должен остаться неизменным.
  Каждая загрузка сохраняется в уникальный путь; не удалять ранее переданные APK.
- Докачка: во время загрузки отключить сеть, затем «Повторить загрузку»: запрос должен содержать `Range` и `If-Range`,
  итоговый SHA-256 должен совпасть. Сменить релиз на сервере — загрузка начинается с нуля.
- Выйти с экрана обновлений во время загрузки и вернуться: загрузка продолжается, прогресс виден.
- Убить процесс во время загрузки: после запуска готовое состояние не выдаётся за выполняющуюся операцию.
- «Разрешить установку» → настройки → назад → «Продолжить установку»; отказ в установщике → APK сохранён.
- Проверить в DEV: канал DEV Beta, загрузка и перезапуск работают так же; GitHub опрашивается только по нажатию.
  CI дополнительно проверяет, что `REQUEST_INSTALL_PACKAGES` присутствует **только в Prod APK**.
- Проверить, что метаданные версии в APK, тег и JSON действительно совпадают.

**Примечание о тестах:** обычный GitHub Actions job компилирует AndroidTest, но
не запускает эмулятор: устройство с API 29/современным API и подписанный upgrade N→N+1
нужно проверять отдельно перед мерджем. Instrumentation тесты запрещено запускать
на телефоне с реальной TDLib-сессией (см. AGENTS.md).

**Ограничение:** Android окончательно проверяет возможность установки, включая ABI,
подпись и соответствие политике ОС. Автоматический APK-install не производится.
