# Ручные обновления Stable

BeyGram Stable (`com.beykus.beygram`) проверяет публичные GitHub Releases **только после нажатия**
«Настройки → Обновления → Проверить обновления». Никаких WorkManager, фоновых запросов,
автоматического скачивания или принудительной установки нет. DEV (`com.beykus.beygram.dev`)
сейчас не поддерживается.

## Публикация Stable-релиза и changelog

1. В PR, который готовит следующую Stable-версию, обновить
   `release-version.properties` (например, до `0.0.0.7`) **и в том же PR**
   добавить человекочитаемый `docs/releases/v0.0.0.7.md`.
   Формат и шаблон: [docs/releases/README.md](releases/README.md).
   Русский текст описывает только проверенные изменения этой Stable-версии.
   Валидация выполняется при изменении версии в PR и перед публикацией:

   ```bash
   python3 scripts/release_notes.py validate
   python3 -m unittest discover -s scripts -p 'test_*.py'
   ```

2. Gradle вычисляет Android `versionCode` по схеме
   `major*100000000 + minor*1000000 + patch*10000 + revision`.
   Допустимые компоненты: major 0–20, minor/patch 0–99, revision 0–9999;
   итог 1–2100000000. Проверить соответствие имени версии, versionCode,
   package name и ключа подписи перед релизом.

3. После успешного CI на **том же коммите `main`** опубликовать тег
   `v0.0.0.7` либо вручную запустить `Android release` из `main`
   с `publish=true` и точной версией. CI **не пересобирает** APK при
   публикации, а использует подписанный артефакт успешной сборки этого SHA.
   Отсутствие файла changelog, несовпадение версий и подписи останавливает
   публикацию.

4. Workflow автоматически дополняет русский текст техническим перечнем PR
   через GitHub Release Notes API (`.github/release.yml`); если GitHub API
   временно недоступен, ставится ссылка на коммит вместо выдуманных изменений.
   Служебный маркер `<!-- TECHNICAL_CHANGELOG -->` отделяет этот перечень:
   GitHub показывает всё, BeyGram в экране обновлений показывает только
   авторскую пользовательскую часть. На клиенте текст разбит на заголовки
   и пункты списка без выполнения HTML/Markdown в WebView.

5. Сначала создаётся **Draft** с описанием, затем загружаются и проверяются
   оба обязательных артефакта, и только после этого Draft публикуется
   (не появится преждевременно в GitHub Releases/latest). При частичном
   сбое можно безопасно повторить публикацию того же Draft. Уже **публичный**
   релиз не изменяется/не перезаписывается этим workflow.

6. Вместе с `BeyGram-0.0.0.7-prod-release.apk` публикуется
   `BeyGram-stable-update.json` вида (пример, реальные хеш и размер CI
   берёт из конкретного подписанного APK):

   ```json
   {
     "schema": 1,
     "versionName": "0.0.0.7",
     "versionCode": 7,
     "apkName": "BeyGram-0.0.0.7-prod-release.apk",
     "size": 70971042,
     "sha256": "<64 lowercase hex SHA-256 of the actual signed APK>"
   }
   ```

Выпуски до поддержки manifest (например, `v0.0.0.3`) не предлагаются
к установке. Для уже существующих опубликованных релизов новый workflow
не меняет APK и описание задним числом. Поскольку на момент внедрения
`release-version.properties` содержит `0.0.0.6`, публикация этой версии
с новым workflow тоже требует **реально составленного** файла
`docs/releases/v0.0.0.6.md`; заглушка автоматически не создаётся.

## Проверки на клиенте

GitHub Releases/latest → существует Stable APK и manifest → валидны версия, имя, размер и SHA-256 →
`versionCode > installedVersionCode` → **по отдельному нажатию пользователя** HTTPS-загрузка →
точный размер и хеш → проверка package name/версии/сертификата через PackageManager →
`FileProvider` → системное подтверждение установки Android.

Не удаляйте текущий BeyGram при ошибке подписи: это удалит локальные данные и TDLib-сессию.
Разрешение «Установка неизвестных приложений» запрашивается только при явной установке.

## Ручной smoke-test на отдельном устройстве

- Подписанный Stable N установлен и залогинен. Обновить до N+1 через экран; сверить,
  что сессия Telegram, медиа и настройки сохранились.
- Установить последнюю версию: ручная проверка должна показать «актуальная версия».
- Проверить офлайн, отсутствие manifest, HTTP 403/429, обрыв загрузки, «Отменить»,
  недостаток места, несовпадение SHA-256 и чужую подпись — установщик не открывается.
- Проверить отказ в Android-разрешении, отказ в установщике, возврат в приложение и повтор.
- На **Android 10 (API 29, ARM64)** и на современном Android запустить
  `StableArchiveSigningAndroidTest` на изолированном эмуляторе/тестовом устройстве:
  проверяется реальное получение подписи архивного APK через тот же код, что использует updater.
  Если `GET_SIGNING_CERTIFICATES` не заполняет `signingInfo` на API 29,
  приложение безопасно переходит к `GET_SIGNATURES`; пустая или чужая подпись — отказ.
- Во время проверки SHA-256 перед установкой быстро нажать «Проверить обновления»,
  затем после открытия системного установщика снова открыть BeyGram и скачать обновление:
  файл, URI которого уже был передан установщику, должен остаться неизменным.
  Каждая загрузка сохраняется в уникальный путь; не удалять ранее переданные APK.
- Проверить в DEV: пункт «Обновления» отсутствует, GitHub не опрашивается.
  CI дополнительно проверяет, что `REQUEST_INSTALL_PACKAGES` присутствует **только в Prod APK**.
- Проверить, что метаданные версии в APK, тег и JSON действительно совпадают.

**Примечание о тестах:** обычный GitHub Actions job компилирует AndroidTest, но
не запускает эмулятор: устройство с API 29/современным API и подписанный upgrade N→N+1
нужно проверять отдельно перед мерджем. Instrumentation тесты запрещено запускать
на телефоне с реальной TDLib-сессией (см. AGENTS.md).

**Ограничение:** Android окончательно проверяет возможность установки, включая ABI,
подпись и соответствие политике ОС. Автоматический APK-install не производится.
