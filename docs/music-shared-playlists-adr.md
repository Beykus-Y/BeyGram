# Совместные плейлисты и перенос библиотеки (ADR)

Статус: решено 15 ноября 2026 г. Совместные подборки не делаем, остаются снимки (вариант A). Код синхронизации не написан. Вариант B возвращается к обсуждению только по отдельному запросу. Перенос библиотеки между устройствами остаётся открытым вопросом владельца (раздел «Решения владельца»).

Область: пункт 7 issue #639 («Совместные плейлисты») и пункт о серверонезависимом восстановлении и экспорте библиотеки. Пункт 8 (BG Media) и экспорт с аудио сюда не входят.

Проверено по базе DEV, коммит 6018116b, 15 ноября 2026 г.

Документ отвечает на два вопроса: как совместная подборка должна работать без собственного сервера и что делать с переносом библиотеки между устройствами.

## Короткий вывод

1. Сейчас плейлисты BeyGram не синхронизируются. `.bgmusic` — это снимок. Получатель получает независимую копию, а повторная отправка может предложить обновление по паре `playlist_id` и `revision`. Ничего не заменяется молча.
2. Файл сам по себе не даёт совместного редактирования. Для него нужны транспорт, роли (владелец, редактор, читатель), приглашения и отзыв доступа, правила конфликтов, история правок и удаление данных. В коде этого нет, и поля под это не заведены.
3. Решение владельца от 15 ноября 2026 г.: оставить снимки, код совместного режима не пишется. Если позже понадобится совместная подборка, идти по варианту B: общий чат Telegram как транспорт, владелец публикует ревизии, участники их читают. Редактирование участниками и собственный сервер отложить.
4. Перенос библиотеки между устройствами не поддерживается. Есть экспорт одной подборки в `.bgmusic` и резервные копии файла библиотеки на этом устройстве. Пакет «вся библиотека» делать только по отдельному запросу.

## Что уже есть в DEV

- Библиотека хранится локально, по одному JSON-файлу на аккаунт (`MusicLibraryJson`, `MusicLibraryFileStore`). Если при чтении часть записей пропущена, перед следующим сохранением создаётся резервная копия. Хранится не больше `MUSIC_LIBRARY_BACKUP_LIMIT` = 3 копий на аккаунт.
- Удаление аккаунта очищает его библиотеку (`MusicLibraryRepository.clearAccount`, `MusicPendingClears`).
- Экспорт работает по одной подборке: один плейлист — один `.bgmusic` (спецификация, раздел 3). Аудио в файл не входит.
- Импорт решает по паре `(playlist_id, revision)`: новая подборка, уже сохранена, обновить или сохранить копией (`BgMusicImportDecision`, `BgMusicImportPlanner`, раздел 10 спецификации).
- Поля, на которые может опереться синхронизация: `MusicPlaylist.revision`, `sourcePlaylistId`, `sourceRevision`, `revisionAtSource`. Владельца, ролей и идентификатора транспорта нет.
- `audioHash` читается из файла, но при экспорте всегда пустой (`BgMusicLibraryMapping`). Хеш не рассчитывается.
- Экспорт с аудио не реализован.

## Требования из issue

- Личный плейлист можно отправить как снимок. Получатель получает независимую копию. Уже сделано.
- Повторная отправка той же коллекции предлагает обновление, без молчаливой перезаписи. Уже сделано.
- Для настоящего совместного редактирования нужно определить: транспорт, права owner, editor и viewer, приглашения, отзыв, конфликты, офлайн-правки, историю и удаление данных.
- Собственный обязательный backend не вводить без сравнения вариантов.
- Локальное хранение без синхронизации не называть облачной библиотекой.

## Варианты

| Вариант | Как работает | За | Против |
|---|---|---|---|
| A. Снимки, как сейчас | Владелец отправляет `.bgmusic`, получатель импортирует. Обновление только при повторной отправке. | Ничего нового. Данные не выходят за пределы Telegram. Сервер не нужен. | Нет совместного редактирования. Ни у кого нет актуальной версии. |
| B. Общий чат Telegram как транспорт | Владелец публикует новые ревизии `.bgmusic` в общем чате, участники открывают последнюю. Редактирует только владелец. | Без собственного сервера. Отзыв через исключение участника из чата. Конфликтов нет, потому что пишет один человек. | Состав подборки видят все участники. Замена файла в уже отправленном сообщении через TDLib не проверена. Обновлений в реальном времени нет. Отзыв закрывает только будущие ревизии: копия, которую участник уже сохранил, остаётся у него. |
| C. Собственный сервер | Аккаунты BeyGram, API, роли, синхронизация. | Настоящее редактирование, роли, история. | Новая инфраструктура и ответственность за данные. Противоречит локальному хранению. Нужно отдельное решение по приватности и стоимости. |
| D. Правки участников сообщениями чата | Каждая правка отправляется сообщением, состояние собирается из журнала. | Редактирование без сервера. | Сложные конфликты, шум в чате, все правки видны участникам, чистый отзыв трудно сделать. |

Решение: вариант A (принято 15 ноября 2026 г.). Вариант B только по новому запросу. Варианты C и D не делать без отдельного решения.

## Вариант B: этапы

Каждый этап — отдельный PR в DEV. Этапы не начаты.

- **B0. Проверка TDLib на двух тестовых аккаунтах** (не на основном). Создать группу, отправить `.bgmusic`, заменить документ в отправленном сообщении, прочитать историю, исключить участника. Результат записать в этот документ. Без B0 код не начинать. Проверку выполняет владелец на устройстве, в облачной сессии её не сделать.
- **B1. Локальная модель.** У плейлиста появляются `shareChatId` и роль `owner`. Сети нет.
- **B2. Публикация.** Владелец отправляет ревизию в общий чат. Побеждает наибольшая `revision`.
- **B3. Чтение.** Участник открывает последнюю ревизию через существующий импорт. При новой ревизии предлагается «Обновить».
- **B4. Отзыв.** Владелец удаляет публикацию. У участника подборка помечается как «больше не публикуется». Локальная копия остаётся.
- **Позже, отдельным решением:** редактирование участниками. Без модели конфликтов не начинать.

## Приватность для варианта B

- По умолчанию в `.bgmusic` нет токенов, приватных путей, номеров телефонов и сведений о приватных чатах (спецификация, раздел 9).
- Названия треков и исполнители видны всем участникам общего чата. Подсказки публичных каналов и автор попадают в файл только при явном включении переключателя при экспорте.
- Общий чат создаёт владелец. Участники видят только опубликованную подборку, но не библиотеку владельца.

## Перенос библиотеки без собственного сервера

1. **Оставить как есть.** Переносится одна подборка через `.bgmusic`. При смене устройства библиотека не переезжает. В текстах не называть её облачной.
2. **Пакет «вся библиотека»** в отдельном формате, не `.bgmusic`, с проверкой как у `.bgmusic`. Нужны решения по шифрованию и лимитам.
3. **Резерв в «Избранном» Telegram.** Файл окажется на серверах Telegram, поэтому назвать его облачной библиотекой BeyGram нельзя. Без явного согласия владельца не делать.

Рекомендация: вариант 1 сейчас. Вариант 2 — отдельным решением, когда появится запрос.

## Вне этого документа

- BG Media (пункт 8 issue): только после проверки качества аудиоанализа.
- Экспорт с аудио: отдельный режим с подтверждением размера, без скрытой выгрузки.
- Хеш аудио: рассчитывать только при реальной необходимости.

## Решения владельца

- **Совместная подборка: оставить снимки.** Принято 15 ноября 2026 г. Вариант B не начинать. Если появится запрос, сначала проводится B0 на двух тестовых аккаунтах.
- **Перенос библиотеки между устройствами: не решено.** Рекомендация: вариант 1. Вариант 2 делать только по отдельному запросу.

## Что не проверено

- Поведение TDLib для групп, замены документов, исключения участников и лимитов Telegram. Нужен эксперимент на тестовых аккаунтах.
- Утверждения о коде проверены по базе DEV 6018116b. Сборка и тесты в облачной сессии не выполнялись: CI остаётся единственной проверкой компиляции.
